## 二、逐条对照

### ① 剔除没有人的画面 —— 已落地

**机制**：`analyzer.build_decision()` 里人物权重最高（`scoring.person_weight`），检出人物即加分保底；释放判定另有硬门 `verdict.release_require_no_person=true`——**没有人物信号就不允许放行**（ADR 0003「按人物信号缺席释放」）。

**实测**：

| 指标 | 值 |
|---|---|
| `has_person=0` | 8,338 条 |
| 其中已移入回收目录 | 7,858 条（覆盖率 **94.2%**） |
| `verdict` = keep / trash / review | 21,817 / 5,714 / 3,607 |
| 反向：`has_person=1` 却已在回收 | 423 条 |

**那 423 条要留意**：有人却被搬进回收目录，只可能来自你手动判 trash（或旧口径遗留）。这是唯一一处"有人的画面被处置"的口子，建议在回收目录里按 `has_person=1` 抽查。

### ② 剔除明显不好的视频 —— 只落地一半 ⚠️

**机制缺位**：`analyzer.frame_stats()` 老老实实算了亮度、对比度、饱和度、**拉普拉斯方差（模糊度）**，还给出 `is_low_light` / `is_blurry` 两个布尔——但它**只在 `_summarize()` 里给 trash 的文案补一句"画面偏模糊/偏暗，请留意漏检"**，**不参与打分、不改变 verdict**。

**实测**（画质差 = `is_blurry` 或 `is_low_light`）：

| 指标 | 值 |
|---|---|
| 画质差合计 | 4,707 条 / 27.11 GB |
| ├ `has_person=0` | 3,813 条（已回收 3,704） |
| └ `has_person=1` | 894 条 ← **保守保留，不删** |
| ⚠ 已回收 **且一次没剪过** | **782 条** |

**怎么理解这个缺口（方向别搞反）**：

- "画质差 + 有人"的 894 条被**保留**——这符合"宁可多留"，不丢数据，只是没省下空间。
- 真正的风险在另一头：模糊会**压低** YOLO 的人物置信度，于是"其实有人但拍糊了"可能被判成无人 → 进回收。上面那 **782 条已回收、既无画面产物也无音频归档**的行，就是这个风险的具体形状。它们可能是真该删的环境误触发，也可能是被糊掉的真人——**现在没有任何产物能让你事后分辨**。

### ③ 保留精彩画面 —— 机制已落地，口径未跑完

**机制**：`highlighter` 两级检测（粗扫 3fps@640 → 精扫 4fps@1280）切三级产物（A/B/C），存到 `G:\change\video-highlights`；`auto_dispose` 让"剪完即搬进回收目录"，你不再逐条看原片（ADR 0001「先剪后删」）。

**实测**：

| 指标 | 值 |
|---|---|
| `highlight_at` 非空（剪过） | 7,036 条 |
| 已在回收目录 且已剪辑 | 6,422 条 |
| 已在回收目录 **但未剪辑** | 1,859 条 |
| `highlight_error` 非空（硬失败） | **0** 条 |
| 产物片段总数 / 时长 | 3,524 段 / 9.8 小时 |
| `highlight_version` 分布 | None 24,102 / `hlv1` 4,825 / `hlv2` 2,211 / **`hlv3` 0** |

**两件事**：

1. **`hlv3` = 0** ⇒ 9/13 修完聚合丢件后升的新口径**一次都没跑过**（`config.json` 已写 `hlv3`，但历史行还停在 `hlv1/hlv2`）。现有 7,036 条已剪行全部"口径不符"，都在重剪队列里。
2. 1,859 条已回收但没剪过，是被硬失败或旧口径漏掉的一批——正是重剪要回收的对象。

### ④ 保留所有可用音频 —— ✅ 已落地（口径 = 有效音频）

> **本节已订正（2026-09-13 11:2x）。** 原判定是「❌ 实质未落地 · 代价最大」，前提是机主原话
> 「保留所有**可用**音频」= "任何存在的音轨"。机主澄清后确认要的是「**有效音频**归档」
> —— 也就是**现行代码的行为**。下面保留取证，但结论已翻转为"不需要改代码"。

**机制**：音频链路本身是齐的——`audioreview.extract_wav()` 抽出 `work_dir/audio/{id}.wav`（16k 单声道 PCM），`archiver.archive_one()` 把它 + 转写文本复制到 `G:\change\audio\<年>\`，附 `manifest.jsonl`。

**门**：`db.archive_queue()` 的谓词是 `speech_present = 1` —— **只有"音频复核确认为有效语音"的处置候选才归档**。这正是机主要的「有效音频归档」。实测**现行队列 = 0 条**：门下的活已干完，没有欠账。


**实测**：

| 指标 | 值 |
|---|---|
| 有音轨 | 31,138 条（100%） |
| `speech_present=1`（进归档范围） | 4,005 条（**12.9%**） |
| 已归档 | 3,616 条 |
| 有音轨但 `speech_present≠1` | **27,133 条** → 不进归档 —— **按"有效音频"口径这是设计如此，不是缺口** |
| └ 其中已在回收目录（无有效语音） | **5,063 条**（实测全部有 wav 缓存；若哪天想做"无语音也兜底"才用得上：+7.06 GB） |
| 已有转写文本却 `speech_present≠1` | 748 条 —— **已逐一复核：有效字数全在 1–3，≥4 的 0 条** ⇒ 是 `min_transcript_chars=4` 那道噪声闸在正常工作，**不是口径瑕疵**（原文档这条判断已撤回） |

> **9/13 复测**（库是活的：DB 口径会漂，文件系统口径稳定）——上表 DB 数字已变为
> 「已在回收目录但未归档 **5,063 条**」「已有转写却 `speech_present≠1` **674 条**」；
> 「原料已在盘上」由推算升级为**实测**：这 5,063 条**全部已有 `{id}.wav` 缓存**（缺 0 条），
> 复制增量 **+7.06 GB**；且**现行归档队列此刻是 0 条**（门下的活已干完，此次放宽是扩口径而非补欠账）。
> 该批构成：`verdict` trash 3,384 / review 1,679、`has_person=1` 386 条、已剪过 3,775 条、时长 65.7 小时。
> 磁盘：`G:` 空闲 81 GB（⚠ 归档目录 `G:\change\audio` 与回收目录**同盘**）、`E:` 空闲 191 GB。
> 另：manifest 里 **540 个 id 被归档过两次**（磁盘 4,157 份 vs 库标记 3,616 条）—— 成因是
> `mark_archived` 在写 manifest 之后调用，进程被杀会留下「文件已写、标记未写」的窗口。
> 归档产物为 16 kHz 单声道 PCM（256 kbps），而源音频仅 ~28 kbps ⇒ **产物约为源音频的 9 倍**。

`speech_present` 的判据在 `audioreview`：VAD 切到语音段且占比 ≥ `vad_speech_threshold`(0.3)，或 ASR 转写出 ≥ `min_transcript_chars`(4) 个有效字。**环境音（脚步、开门、犬吠、孩子哭）一律不算**——它们没有"语音"。
> 这**不是缺陷，是口径**：机主要的是「有效音频」。若将来想要"环境音也兜底"，那是一次**需求变更**（代价与做法见 §四「建议行动」）。

**好消息：原料已经在盘上了。**

| 指标 | 值 |
|---|---|
| `{id}.wav`（归档取的就是这个） | **9,589 个** |
| `{id}.dsp.wav`（ASR 降噪副本） | 7,379 个 |
| 合计 | 16,968 个 / **23.35 GB** |
| 其中 `speech_present≠1` 且未归档 | **5,584 个**（已在回收目录 4,930 / 未回收 654） |

**保真度不是问题**：抽样 3 条源片 ffprobe → `aac / 8000 Hz / mono / ~28 kbps`。归档取 16 kHz 单声道 PCM，**相对 8 kHz 源是无损的**（监控源本就只有 4 kHz 带宽）。
> 边界：将来若换 48 kHz 立体声源，16 kHz 抽取就会有降采样损失——那时这条要重估。

## 三、两个真缺口（按代价排序）

> 原本是三个。**G1 已撤回**（前提被机主澄清 + 证据被复核证伪），理由见下。

**~~G1 · 音频兜底只认"人声"~~ —— 已撤回，不是缺口**
原判据建立在"可用音频 = 任何存在的音轨"这个读法上。机主明确要的是「**有效音频**归档」，而现行代码正是这个口径（`speech_present=1`，队列 0 条）。原用来加重的第二条证据 —— "748 条已有转写文本却被判无语音 = 明确的口径瑕疵" —— **已被证伪**：那 748 条的有效字数**全在 1–3 字**（`'嗯。'` `'啊。'` `'哦。'` `'The。'`），**≥4 字的 0 条**，正是 `min_transcript_chars=4` 在正常工作。
> 唯一的残留风险**不在代码而在流程**：归档吃的是音频复核的缓存 wav ⇒ **必须在清空回收目录之前跑完「音频复核 + 归档」**（一键流水线已按 复核→归档→放行→剪辑 排序，见 ADR 0004）。

**G2 · 782 条"零保全"行**
画质差 + 无人 + 已在回收 + 一次没剪过 = 删了就真没了，且**无任何产物可事后复核**。无法从数据判断它们是"真该删的环境误触发"还是"被糊掉的人"。

**G3 · 精彩画面口径落后一整版**
`hlv3` 跑了 0 条。聚合丢件修完（留存率 42% → 79%）但**收益还没落到任何一条真实数据上**——没跑就是个未兑现的承诺。

## 五、验证与边界（这份审计能证明什么、不能证明什么）

**已验证**：
- 每条结论都由 `scripts/audit_requirements.py` 从**当前库**现算；关键数字另用一次独立查询交叉核对，两路一致。
- 音频保真度结论来自对 3 条源片的 `ffprobe` 实测，不是推测。
- 代码侧的机制描述对到**函数名**（`build_decision` / `frame_stats` / `archive_queue` / `archive_one` / `extract_wav`），不依赖行号（行号最容易失真）。

**不能证明**：
- **不代表回收目录里的内容"可以删"** —— `待保全` 归零才是那个信号，见 `docs/开发计划-删除前精华保全.md`。
- **782 条是否属于误删，本审计无法判定**（数据里没有"这条到底有没有人"的独立真值）。它只指出"这批删了没有回看余地"。
- 未做端到端重跑；③ 的"跑完能到多少"是**推算**，不是实测（④ 已结案，不再涉及推算）。
- 抽样 3 条源片只代表抽样时刻的编解码参数，不代表全部 31,138 条的分布。
