## 一、结论

**不需要改代码。** 机主要的「**有效音频**归档」，就是代码现在的行为：

- 门 = `db.archive_queue()` 的 `speech_present = 1` —— 「音频复核确认为**有效语音**」的处置候选才归档；
- 实测**现行队列 = 0 条**：门下的活已干完，**没有欠账**。

所以 ④ 这条诉求**已落地**，不是缺口。

## 二、为什么之前判断"要改"，以及那份判断怎么被推翻的

上一轮把机主原话「保留所有**可用**音频」读成了"任何存在的音轨"，于是把 `audio_checked=1 & speech_present=0` 的处置候选当成"被门挡住的损失"，并把其中"**已有转写文本**"的那批称为**"明确的口径瑕疵"**。

**这条证据已被复核证伪：**

| 复核项 | 实测 |
|---|---|
| 全库 `audio_checked=1 & speech_present=0 & 有文本` | 748 条 |
| 其有效字数（`audioreview._effective_chars`，去空白与标点）分布 | **1–3 字：748 条；≥4 字：0 条** |
| 抽样文本 | `'嗯。'` `'啊。'` `'哦。'` `'我懂。'` `'没有。'` `'The。'` |
| 对照：`speech_present=1` 的文本分布（前 200 条） | `≥10` 字 108 条 / `≥4` 字 48 条 / `1–3` 字 34 条 / 空 10 条 |

**有效字数 ≥4 的一条都没有。** 这 748 条是 ASR 在噪声上的**幻觉碎片**；判 `speech_present=0` 正是 `audio.min_transcript_chars=4` 那道闸在**正常工作**，不是"有内容却不给留"。⇒ 口径自洽，无需修改。

## 三、唯一还站得住的改动（可选，且与音频口径无关）

**C5 · `manifest.jsonl` 相对路径化** —— 机主明确「后期整理完成后会把归档目录整体搬到专用盘」，而 manifest 里存的是**绝对路径**（实测：`"wav": "G:\change\audio\2015\xxx.wav"`）。搬完这两个字段**静默失效**。

- **落点**：`archiver.archive_one()` 的 `record`；`wav`/`txt` 改存相对归档根的路径（`2015/xxx.wav`），可另加 `archive_root` 标明产出根。
- **代价**：2 行。**目前没有任何代码读归档 manifest**（只有写 + `selftest` 断言 id/转写/回收路径三个字段；`_legacy/backfill_sent.py` 读的是**精华**的 manifest），所以改动不破坏调用方。
- **不做也行**：目录结构（年份 / 同名 stem）本身足以辨认。

## 四、「明确不做」清单

| 不做 | 理由 |
|---|---|
| **放宽归档门为 `has_audio=1`** | **已撤回** —— 前提（"可用音频 = 任何音轨"）与证据（748 条口径瑕疵）双双被证伪。若将来真想放宽，见 §五。 |
| 归档格式 16 kHz PCM → opus | 产物 256 kbps 而源音频仅 ~28 kbps ⇒ 产物约为源 9 倍，确有 9x 空间；但有效语音归档的增量本就小、`G:` 尚余 80.6 GB，且机主计划搬去专用盘 ⇒ 收益不抵"归档 = 原样留存"这一简单心智模型被破坏的代价。 |
| 「画质差」参与打分/判定 | `is_blurry` 4,677 条中 3,804 条本来就无人才被判删；只剩 **873 条「糊但有人」**（`is_low_light` 同形 2,931/461）⇒ ② 已被"无人即删"覆盖，画质只承担解释职责（`feedback.py` 已接）。而那 873 条**恰恰不该因为糊就删** —— 那是唯一的线索。 |
| 缓存 wav 缺失就现抽音轨 | 实测这批缺 0 条；加了它等于在剪辑之外再引入一条 ffmpeg 路径与"源片是否还在"的分支。 |
| 全库 27,522 条都兜底 | 未归档 27,522 条中 21,549 条要现抽音轨、约 +38 GB，且大多**是不打算删**的视频（本体自带音轨）⇒ 重复留存。 |
| 清理那 540 份重复归档产物 | 无害、无收益，且要动归档目录（删除属机主手动范畴）。只在下方留成因。 |

## 五、如果你哪天改主意（想连"无有效语音"的片段也兜底）

那才是"放宽门"，改动仍是 **2 行 SQL**，但**门必须写成 `has_audio=1 AND audio_checked=1`**：

- **落点**：`db.archive_queue()` + `db.count_archive_pending()`（两处必须同时改，否则又是"计数与队列口径不一致"那类错报）；
- **为什么必须带 `audio_checked=1`**：`archive_one` 对没有缓存 wav 的行返回 `skipped`，而**队列看不见文件系统**。若只写 `has_audio=1`，将来新扫描进来、尚未音频复核的行会"进队列 → 被跳过 → 又留在队列里" ⇒ UI「待归档」永远归不了零。写成 `audio_checked=1` 后语义反而干净：**复核过 ⇒ 有 wav ⇒ 必归档**；
- **实测代价**：5,063 条 / **+7.06 GB**，**原料全在盘上**（这 5,063 条全部已有 `{id}.wav` 缓存，缺 0 条）；构成：trash 3,384 / review 1,679、`has_person=1` 386 条、已剪过 3,775 条、时长 65.7 小时；
- 配套需同步：`ui.py` 文案（「有效语音」→「已复核音轨」）+ 一条自检钉住新口径。

## 六、④ 的真风险不在代码，在流程

- **归档吃的是"音频复核的缓存 wav"**，不是视频本体 ⇒ 若在音频复核跑完前清空回收目录，未复核行里的有效语音就真丢了。一键流水线已按 **复核 → 归档 → 放行 → 剪辑** 排序（ADR 0004），单独点也必须守这个顺序。
- **归档目录与源片同父目录**：源 `G:\change\2015|2016`、回收 `G:\need-del`、归档 `G:\change\audio` ⇒ 别顺手清 `G:\change` 整个目录。
- 归档目录位置由设置里的 `archive.dir` 决定；机主后期会整体迁到专用盘（⇒ 才引出 C5）。

**540 份重复的成因**：`archiver.archive_pending` 里 `mark_archived` 在 `mf.write` **之后**调用 ⇒ 进程被杀会留下「文件已写、标记未写」的窗口，下次重跑以 `_<id>` 后缀再复制一份。**不是活 bug**（`archived_at` 现在挡得住重跑），但**若清了 `archived_at` 重跑，产物会再翻一倍**。

**复现**：`./.venv/Scripts/python.exe scripts/audit_requirements.py`；或直接跑下面的 SQL。

```sql
-- 处置候选（与 db._PENDING_OR_TRASHED 同口径）
--   (human_decision='trash' AND trash_path IS NOT NULL)
--   OR (human_decision IS NULL AND verdict IN ('trash','review') AND meta_ok=1)

-- 现行队列（本次实测 = 0）
SELECT COUNT(*) FROM videos WHERE (<处置候选>) AND speech_present=1 AND archived_at IS NULL;

-- 若要放宽，这才该是队列（另一口径，本次实测 5,063）
SELECT COUNT(*) FROM videos WHERE (<处置候选>) AND has_audio=1 AND audio_checked=1 AND archived_at IS NULL;

-- 复核"748 条是否真是口径瑕疵"：有效字数 ≥4 的有几条
SELECT COUNT(*) FROM videos WHERE audio_checked=1 AND speech_present=0
  AND COALESCE(transcript_text,'') <> '';   -- 748 条；逐条算 _effective_chars 后 ≥4 的为 0
```
