## 一、结论先行

**1. 工程底子是好的，主要问题不在代码，在"已经做对的设计没有落地执行"。**
分层清晰（scanner/analyzer/highlighter/mover 各司其职）、队列幂等、
有 selftest 回归 + smoke_ui、有 ADR 记录"为什么"。这套东西的**设计质量高于完成度**。

**2. 三个最高杠杆的动作（按紧迫度）：**

| # | 动作 | 为什么现在 | 成本 |
|---|---|---|---|
| 1 | **先跑 hlv2 重剪，再手动清空回收目录** | 474 条视频"粗扫看到过目标、最终零产物"；它们的原片**已经躺在 `G:\need-del` 里**。4,567 个文件仍未被删——**这个机会窗口一关就永久关闭**。ADR 0006 已把这条写死：「存量重剪完成前不得手动清空回收目录」 | 重剪 816 条 ≈1.5h；删是手动 |
| 2 | 统一 data 根路径（现在分裂成两条） | 删错任何一个"看起来像残留"的目录，视觉链路会直接停摆 | ~30min |
| 3 | 一键放行 3608 条「无人」候选 | 审核台 4321 条待办里，3608 条人工盯着的正是机器抽的那 16 帧，逐条审不产生信息 | 点一下 |

**3.「按周/按月出成片」能做，而且已经跑通了。**
`scripts/compile_period.py` 用现有产物拼出了 **2015-12（145 段 / 19.5 分钟 / 183 MB / 138 s）**
和 **2016-W04（103 段 / 14.1 分钟 / 114 MB / 109 s）**，零失败。
它不是 L2.8 的功能扩展，而是一个**独立的下游模块**——详见第四节。

## 三、问题清单（按杠杆排序，每条都有实测支撑）

### P0 · 会丢东西或会停摆

#### 1. hlv2 重剪一次都没跑，而原片已进入待删队列

`videos.highlight_version` **4,825 行全是 `hlv1`**。hlv1 口径下：
- 粗扫看到目标、精扫没确认 ⇒ **信号直接丢弃** → 474 条视频"最终零产物"
- C 级只留静帧不切 mp4 → 394 条视频只有图片，没有可回放的片段

而这批原片已经全部被自动移入 `G:\need-del`（4,567 个文件，25.6 GB，**一个都没被删**）。

**"程序只移动不删除"这条安全设计，正好把抢救窗口完整地留着。**
一旦手动清空 `G:\need-del`，这 816 条（474 零产物 + 394 仅静帧，按计划文档口径）的内容就永久消失。
`docs/开发计划-删除前精华保全.md` 里 P2 标注的 ⚠️「实机 A/B 试点（第一批 816 条重剪）尚未执行」，
是整份文档里唯一一条"代码就绪、就等在运行窗口"的待办，也是当前**最值钱的 1.5 小时**。
（这条判断已写进 ADR 0006 的 Consequences，不是本报告新提出的。）

#### 2. data 根路径分裂成两条

| 用途 | 实际路径 | 内容 |
|---|---|---|
| `runtime.sqlite_path` | `E:\code\video-search\data` | **240 MB 数据库** |
| `ROOT/data`（config.py 算出：thumbs/models/probe） | `E:\code\video-search\data` | **缩略图 31,136 张 / 5.1 GB** |
| `work_dir` / `yolo_model_path` / `audio.model_dir` | **`E:\video-search\data`** | **音频缓存 14,906 个 wav / 20.8 GB**、YOLO 模型 10 MB、`highlight_frames` 残留 |
| 精华产物 / 语音档案 | `G:\change\video-highlights`、`G:\change\audio` | 1.35 GB / 0.90 GB |

现在能跑，纯属两条路径都还在。但：
- `yolo_model_path` 指向 `E:\video-search\data\models\yolov8n.onnx`。**删掉这个"看起来像旧副本"的目录
  → `check_ready` 直接报"未找到 YOLO 模型"，L1 与 L2.8 全线停摆**（`E:\code\...\models` 里那份副本配置根本没指向）。
- 20.8 GB 的音频复核缓存也躺在那里，没人知道它在那儿。
- `highlight_frames` 里有 165 个残留文件 → 说明有过一次未走完 finally 的中断。

**建议**：把 `work_dir` / `yolo_model_path` / `audio.model_dir` 统一改到 `E:\code\video-search\data`
（DB 已在那儿，且 `ROOT/data` 是与代码强绑定的那一个），迁移 20.8 GB 音频缓存后清掉旧树。
顺手把 `E` 盘 194 GB 余量用在刀刃上——**G 盘只剩 81 GB，而 hlv2 重剪预计新增 ~15 GB、
2016 还有 125 GB 源素材待处理**（推断：空间是下一个卡点）。

#### 3. C3「C 级不进审核队列」当前是空转的

`highlight_best_grade` 是后加的列，**1,045 行全部为 NULL**（hlv1 那批从没写过它）。
而 C3 的过滤条件是：

```sql
COALESCE(highlight_best_grade, '') <> 'C'
```

NULL → `''` → 恒真 ⇒ **一条都没被滤掉**。也就是说"C 级是档案不是待办"这个设计
目前**没有生效**，要等重剪把版本刷到 hlv2 才自愈。
（`highlight_best_grade` 的计算用 `min()` 是**对的**——A/B/C 的字典序恰好等于级别序——但很晦涩，
建议换成显式映射，否则下次改级别名就静默错。）

#### 4. `highlight_count` 与 `highlight_sec` 口径不一致

- `highlight_count = len(clips)` → **含**只有静帧、没有 mp4 的 C 段
- `highlight_sec = sum(dur for c in clips if c["file"])` → **不含**

实测 **394 / 1,045 条对不上**（例：`count=2`、有文件段数 `0`、`sec=0.0`）。
UI 上"切出 2 段"会让人以为有两段视频可看，其实是两张图。

#### 附（2026-09-12 补记，已修）：`cut_one` 里 `scanned` 未初始化 → 1,382 条"静默漏检"

`src/highlighter.py` 的 `cut_one` 把 `scanned` 定义在 `if fine_on and c_hits:` **里面**，
而合并两级结果时无条件引用它。而「粗扫零命中」恰恰是最常见的一类（帧差预筛整片跳过 +
确实没有目标）。实测库里的失败分布：

| 失败原因 | 条数 |
|---|---|
| `UnboundLocalError: cannot access local variable 'scanned'` | **1,382** |
| 抽帧失败（无法解码） | 23 |
| 视频文件已不存在 | 10 |

**为什么这条比普通 bug 贵**：`highlight_queue` 与 `rehighlight_queue` **都**要求
`highlight_error IS NULL`。一旦踩中，这条视频既不进正常队列、也不进重剪队列 ——
它从两边的视野里同时消失，而库里看起来只是"失败了几条"。所以它同时也是
"待剪辑 0 条"这类错觉的成因。

已修（`scanned` 提到 `if` 之外初始化），并在 `selftest` 里加了回归项
`test_coarse_zero_hits_no_crash`。**存量 1,382 条需要用「重置失败记录」放回队列**，
否则它们永远不会被重新处理。

### P1 · 该做但不紧急

| # | 问题 | 说明 |
|---|---|---|
| 5 | **抽帧落盘再读回** | `highlighter._extract` 用 ffmpeg 写 jpg → `cv2.imread` 读回。每条视频上百张 jpg 的写+读。改 `-f image2pipe -vcodec mjpeg -` 管道直接进内存，能省掉这部分磁盘 IO——它在单条 6.1 s 均值里占相当一块（推断） |

## 四、周期合辑：能做，已跑通

### 4.1 定位边界

| 模块 | 职责 |
|---|---|
| `src/highlighter.py`（L2.8） | **检索 + 切割**：找出"哪几秒有价值"，切成一个个 mp4 |
| `scripts/compile_period.py`（新增） | **编排 + 拼接**：把某周/某月的片段按时间顺序串成一条片子 |

两者不重叠：highlighter 不做时间线，编译器不碰检测。
按项目术语惯例（`CONTEXT.md`），它**不该叫"精华剪辑"**，
建议命名为 **「周期合辑」/「周记」**，与「画面精华」并列而非从属。

### 4.2 实测结果（真实数据，零失败）

| 期号 | 片段 | 时长 | 体积 | 耗时 | 级别构成 |
|---|---|---|---|---|---|
| 2015-12（月） | 145 | **19.5 分钟** | 183 MB | 138 s | A 58 / B 87 |
| 2016-W04（周） | 103 | **14.1 分钟** | 114 MB | 109 s | A 44 / B 59 |

产物：`{期号}.mp4` + `{期号}.manifest.json`（每段来源/时刻/级别/置信度）+ `{期号}.节目单.txt`。
成片规格校验：`h264 1280×720 yuv420p` + `aac 48000Hz 单声道`，`+faststart`。

**可编期分布**：按月 13 期（2015-06 ~ 2016-06），按周 37 期。
按月时长从 0.1 分钟（2015-06）到 51.3 分钟（2016-01）；按周 0.1 ~ 14.5 分钟。

### 4.3 设计要点——以及为什么必须这么做

**① 两遍法，不能一条命令拼完**
一次 `filter_complex` 拼 327 段会撞 **Windows 命令行 32K 字符上限**
（2016-01 有 327 段，光路径就 ≈2.6 万字符）。所以：

```
pass 1  逐段归一化转码（分辨率/帧率/像素格式/采样率/声道统一，无音轨补静音）
pass 2  concat demuxer + -c copy（秒级完成）
```

附带好处：pass 1 的中间片段可复用，改顺序/换片头不必重新解码源片。

**② 必须归一化三个维度，不能赌"参数一致"**
当前 845 段恰好全同规格，`-c copy` 能直接拼。但那是**单一机位 + 单一 DVR 编码**的运气：
- 分辨率/像素格式不同 → 拼接直接失败
- 帧率不同 → 时长漂移、音画不同步
- 采样率/声道不同 → 音频拼接失败

归一化后，这些变成被保证的约束，而不是"应该没问题"。

**③ 无音轨必须补静音**
`highlighter._cut` 对无音轨源加 `-an`。若成片里同时有"有音轨段"和"无音轨段"，
concat 会因**流数量不一致**失败。当前 4,825 条源全部 `has_audio=1`，
所以这个问题现在不会暴露——但换个机位、或某段源没音轨，就会迎面撞上。

**④ C 级默认不纳入**
476 段 C 里绝大多数是**纯动静**（`conf=0.0`，只有帧差没有目标），
拼进去就是一串莫名其妙的画面抖动。默认只取 A/B（`--grades A,B`）。

**⑤ 必须用 `shot_at`，不能用 mtime**
`mtime` 是拷贝时间，`shot_at` 才是拍摄时刻。845/845 段都有 `shot_at`（从文件名时间戳解析），
所以按周/按月分组零障碍。**这是这套流水线最被低估的一笔资产**——
绝大多数家庭影像整理工具就是死在"不知道这段是什么时候拍的"。

**⑥ 跨年周要按 ISO 定义**
`2015-W53` 与 `2016-W01` 已正确分开。若按"日历周"粗暴切，
12 月底到 1 月初那一周会被劈成两半，成片出现断点。

**⑦ 单段时长上限（默认 20 s）**
一条 51.8 秒的长段会独占成片——而它本身就是 highlighter `keep_full_ratio`
会改判"整片保留"的那类。默认把它排除在合辑之外（实测 2016-W04 的 104 段因此变 103 段）。

### 4.4 距离"成品"还差什么

| 项 | 现状 | 工作量 |

### 4.5 用法

```bash
cd E:/code/video-search

# 看有哪些期可编
./.venv/Scripts/python.exe scripts/compile_period.py --list
./.venv/Scripts/python.exe scripts/compile_period.py --by week --list

# 只算计划不产出
./.venv/Scripts/python.exe scripts/compile_period.py --by month --plan

# 出一期（默认输出 work_dir/compilations）
./.venv/Scripts/python.exe scripts/compile_period.py --by month --value 2015-12
./.venv/Scripts/python.exe scripts/compile_period.py --by week  --value 2016-W04 --grades A

# 限制每期时长（超过预算按价值取舍）
./.venv/Scripts/python.exe scripts/compile_period.py --by month --value 2016-01 --max-minutes 20
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--by` | month | month / week（ISO 周） |
| `--value` | 空=全部期 | 期号：`2015-12` / `2016-W04` |
| `--grades` | `A,B` | 纳入级别（C 是噪声档案，默认排除） |
| `--max-minutes` | 0=不限 | 每期时长上限，超预算按价值取舍 |
| `--per-clip-cap` | 20 | 单段时长上限（秒），防长段独占 |
| `--out` | `work_dir/compilations` | 输出目录 |

**安全边界**：只读源片与数据库；只写 `--out` 下的自创文件；输出目录为盘符根目录时拒绝执行；

## 六、结论与不确定性

**判断**：这个项目的瓶颈已经**不在"检测准不准"，而在"编排与执行"**——
数据已经证明检测链路能捞回 L1 漏掉的人（0.80 置信度的赤膊真人、穿粉红衣服的小孩），
而 4,825 条产物里 100% 还是旧口径、3,608 条候选等人点、
20.8 GB 缓存躺在一条随时可能被当垃圾清掉的路径里。
**把已经做对的事跑完，收益大于再写新功能。**

**不确定的地方（诚实标注）**：
- P1#5（抽帧 IO 占比）、P1#6（批量化提速幅度）是**推断**，我没有做 profiling，需要实测才敢定收益。
- P2#13（预筛跳过的 2,832 条是否真"无人"）**无法从现有数据判断**——它们一帧都没跑过检测。
  这是本报告里最大的一个未知，也正因如此值得抽样复核。
- 所有"文件还在"的判断（4,567 个）以 `G:\need-del` 未被手动清空为前提，是**时点快照**。
- 周期合辑脚本是**原型**：未进 `src/`、未接 UI、未写回归测试。转正前应先补测试用例。
