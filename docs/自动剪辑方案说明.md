## 一、结论先行

这套东西的本质**不是剪辑，是检索 + 切割**。

剪辑软件（剪映/PR）解决的是"已知素材怎么拼好看"，而你的问题是反过来——
**不知道素材里哪几秒有价值**。所以核心不在剪辑工具，而在一条把
「17.9 小时 → 几百个可用片段」的检测流水线。

```
粗扫抽帧 → CLAHE → 帧差预筛 → 检测(0.15) → 候选窗
        → 精扫抽帧 → 检测(0.25) → 事件聚合 → 分级 → 切割/抽帧 → 复核页签
```

**全自动，不需要人工二筛。** 机器把不确定性表达在目录结构里（A/B/C 三级），
你想看就看 A 级，不看也无所谓——这是 v1 到 v2 最大的设计变化。

## 二、素材底数（实测，非估算）

| 指标 | 实测值 |
|---|---|
| 待处理（已判 trash 待删） | **1372 个 mp4** |
| 总时长 | **17.9 小时** |
| 单文件时长 | 平均 47s |
| 编码规格 | H.264 / 1280×720 / **15fps** |
| 命名规则 | `YYYYMMDDHHMMSS_010.mp4`（含真实拍摄时间，通道号 010） |
| 月份分布 | **2015-12 占 1321 段（96%）**；2015-06~11 合计 51 段 |
| 时段分布 | 夜间(18–06) **73%**；其中 19–21 时集中 894 段（65%） |
| 机位 | 鱼眼门镜摄像头，广角形变明显 |

环境现状：ffmpeg 8.1 ✅、Python 3.13 ✅、显卡 **RTX 3070 Ti**。
注意两端走的不是同一条路：**抽帧解码**用 `-hwaccel auto`（有 N 卡走 CUVID）；
**YOLO 推理**走 `cv2.dnn.readNetFromONNX`，**未启用 CUDA backend，仍是 CPU 路径** ——
所以下面所有推理耗时都是 CPU 口径，换 GPU backend 是潜在但未做的优化。

### v1 的两处结论被实测推翻

1. **规模不是 88 分钟，是 17.9 小时。** v1 基于 113 段抽样，实际全量 12 倍。
   这直接否掉了"一把梭 20 分钟"的工期估算。
2. **不是 94% 夜间红外。** 按文件名时间戳统计，夜间占 73%，另有 27% 是彩色
   昼间画面（室内开灯/自然光）。v1 的"红外热源更亮"假设只在夜间那部分成立。
   两类素材混跑已被 30 样本验证覆盖，无需分批处理。

### 一个必须先摊开的信号

L1 判定结果里，1372 段中 **83% 的 `retention_score = 0`，且 `near_miss` 为 0/1372**。
`near_miss` 记录的是"模型看到了人但置信度没过阈值"——一条都没有，意味着在 L1
的视角里这批画面是真空的。

这个数字指向两种相反的可能：画面确实空，或者模型在低照度下瞎了。
**这正是本功能存在的理由**：用 8 倍于 L1 的采样密度独立复核一遍，
用数据回答"到底有没有东西"。

## 三、关键约束

### 3.1 L1 采样密度不足（本功能的第一动机）

L1 每段只抽 `analysis.sample_frames` 帧（当前配置 **15**，代码默认 6）。43 秒 × 15fps = 645 帧，
**只有约 2.5% 的画面被看过**。抽查页给你看的就是这十几帧 —— 也就是说
**抽 10 条抽查 ≈ 只看过 100 多秒的画面**，而"没看过"的那 97.5% 才是风险所在。

小孩身形小、进出画面快，或者被门框家具挡住只剩半个身子——这种密度必然漏。
**所以"抽查过 10 条"兜不住这个漏。** 自动化高密度检测不是重复劳动，
是替人补上没看过的那 97.5%。

样本验证已证实：一条 L1 判 0 分的视频里，两级检测捞回了**穿粉红色衣服的小孩**。

### 3.2 低照度掉点

COCO 训练的通用检测器在低照度画面上 person 类明显掉点。三重对冲：

- **CLAHE 预处理**（必开）：对比度受限自适应直方图均衡，拉开信噪比
- **帧差预筛提供第二路证据**：不依赖模型，纯像素差分
- **阈值下调**：误检代价远小于漏检——漏掉的家庭影像找不回来

### 3.3 固定机位 = 帧差预筛的理想工况

固定机位、无云台运动，背景几乎恒定。先用帧间差分找出"画面有变化"的时间窗，
只对这些窗口跑检测。**样本实测省 93% 算力**（4042 帧只送检 267 帧），
远好于 v1 预估的 40–60%。

> 备选方案（已评估，不采用）：
> - **OpenCV HOG 行人检测**：零依赖，但低照度下几乎失效
> - **纯背景减除**：能定位运动，但分不清人/宠物/拖把/光影，只能做候选区间
> - **微调红外专用模型**：效果最好，但为家庭素材做模型微调属于过度工程

## 四、两级检测（v2 核心设计）

### 为什么不能单级

| 方案 | 单视频推理 | 全量 1372 段 |
|---|---|---|
| 2fps @640（v1 原设计） | 11 s | ~4.3 小时 |
| 2fps @1280（全片精扫） | 46 s | ~17 小时 ❌ |
| **两级：粗扫 + 精扫** | **~7 s（实测）** | **~2.7 小时** ✅ |

直接把全片拉到 1280 精扫是 17 小时，不现实。两级能在 1/6 的代价下拿到接近的召回。

### 两级分工

| 级 | 参数 | 范围 | 职责 |
|---|---|---|---|
| 粗扫 | **3fps @640，conf 0.15** | 全片 | 负责**不漏**，误检交给下一级 |
| 精扫 | **4fps @1280，conf 0.25**，窗两侧各扩 2s | 仅候选窗 | 负责**看清**，小目标全靠它 |

粗扫阈值压到 0.15 是故意的：**误检的代价是被精扫过滤掉（多花点算力），
漏检的代价是家庭影像永久消失。这两件事不对等。**

### 精扫预算控制

精扫帧数上限 = 粗扫帧数 × `max_fine_ratio`（默认 1.5）。超预算时按粗扫得分
从高到低优先精扫。**被预算跳过的窗不会当作"已复核"丢弃**——它们的粗扫检出
保留为 C 级疑似（要求该帧确实有动静，静态画面上的疑似基本是噪点）。

样本实测：精扫否决了 5 段粗扫误报，两级协作真实生效。

## 五、事件聚合与三级产出

### 5.1 离散帧 → 事件

| 参数 | 取值 | 说明 |
|---|---|---|
| `gap_merge` | 3.0 s | 间隔小于此值的有检帧合并为同一事件（抵消遮挡抖动） |
| `min_duration` | 1.0 s | 短于此的事件丢弃 |
| `pre_pad` | 2.0 s | 起点前移，避免人物"半路冒出来" |
| `post_pad` | 3.0 s | 终点后移，动作收尾完整 |
| `max_clips_per_video` | 8 | 单视频最多切几段（按价值排序） |
| 边界钳制 | [0, 时长] | 防止越界 |

### 5.2 三级产出（用目录结构代替人工筛选）

| 目录 | 判定条件 | 产物 |
|---|---|---|
| `A_确认/` | 精扫确认有目标，**且 ≥8s 或 ≥2 人同框** | mp4（含原音）+ 代表帧 |
| `B_短暂/` | 精扫确认有目标，但 <8s 且 <2 人 | mp4（含原音）+ 代表帧 |
| `C_疑似/` | 粗扫看到但精扫未确认（hlv2 起降级保留；**hlv3 起含孤立的单帧检出**），**或只有大幅动静**（开关门/物品倒地） | **mp4（含原音）+ 3 张代表帧**（hlv2 起；可关） |

**C 级从"只留静帧"改成"切 mp4"是 2026-09-10 的转折。** 原设计认为 jpg 几乎不占空间、
留证足够；但实测发现 **474 条视频"粗扫明明看到东西、最终零产物"** —— 静帧之外的动态
信息（人怎么走的、动作幅度多大）全丢了。既然精华剪辑的定位是**原片被删前的最后一道
保全**，宁可多占空间也要留下可播放的片段。两个开关可一键退回：
`highlight.c_cut_mp4`（C 级切 / 不切 mp4）、`highlight.keep_coarse_suspect`（粗扫命中是
降级保留还是按旧行为丢弃）。

> 注：C 级语义一路在变 —— v1 是"<2s 丢弃"，v2 改为"疑似但留证"，**hlv2 进一步改为
> "疑似也切 mp4"**，**hlv3 补上"孤立检出也算"**（见 5.4）。每次改动都是同一个方向：
> 少丢东西。三次里有两次事后证明"以为修好了、其实还有一层"——所以每改一次都要拿
> **现库产物**复核一遍（`db.no_clip_breakdown()`、回收目录三堆），别信文档自述。

### 5.3 原片子档：已剪辑 / 待保全（2026-09-12 定，09-13 扩）

三级目录管的是**产物**摆在哪；这一节管的是**原片**摆在哪。

原片剪完之后会被自动移入回收目录（`highlight.auto_dispose`），落点是
`回收目录\A_高置信_可批量删除\<年>\<原目录>\`。问题是这一堆里混着**性质完全不同**的东西。

机主是**手动**删除的，打开回收目录只回答一个问题：**「这一条我现在能删吗」**。
所以分堆不按"剪过 / 没剪过"（那会把可闭眼删的和删了就没了的一锅端），按**三态**：

| 子档 | 状态常量 | 判据 | 机主该做什么 |
|---|---|---|---|
| `已剪辑\` | `STATE_CLIPPED` | 有 A/B 产物，**且产物文件此刻仍在** | 逐条扫一眼，确认剪得对 ⇒ 删 |
| `待保全\` | `STATE_PENDING` | 还没剪完（从没剪过 / 硬失败 / 版本落后且症状命中重剪队列） | ★ **一个都别删**，先跑剪辑与重剪 |
| （不进子档） | `STATE_PLAIN` | 剪过、无 A/B 产物 | 可整批直接删 |

```
回收目录\
├─ 已剪辑\                     ← 有 A/B 产物待验
│   ├─ A_高置信_可批量删除\2015\20150623\xxx.mp4
│   └─ B_低置信_建议抽查\2016\20161218\xxx.mp4
├─ 待保全\                     ← ★ 精华还没落袋，一个都别删
│   ├─ A_高置信_可批量删除\...
│   └─ B_低置信_建议抽查\...
├─ A_高置信_可批量删除\        ← 机器剪过、无 A/B 产物（可闭眼删）
├─ B_低置信_建议抽查\
└─ _reports\
```

**`待保全` 归零，才是"可以放心清空回收目录"的信号**；顺序永远是
**先跑完剪辑/重剪，再对齐子档**（反了就等于按旧事实贴标签）。

四个必须记住的点：

1. **子档名不带字母，是刻意的。** 回收档位的 A/B（`A_高置信_可批量删除` / `B_低置信_建议抽查`）
   说的是"AI 判不判得出能不能整批删"，画面精华的 A/B（`A_确认` / `B_短暂`）说的是
   "剪辑置信度"——两套彼此无关。写成 `已剪辑_AB\A_高置信_可批量删除\` 就有两个 A、两个 B，
   半年后自己读不出来。术语表里已把这个歧义钉死（见 `CONTEXT.md`）。
2. **判据是"剪出 A/B 级产物 + 产物文件此刻仍在"**，不是看 `highlight_best_grade` 字段
   （只有新写入的行才有值，老行全 NULL，拿它筛会漏掉绝大多数）。C 级不算——它是档案不是待办；
   产物已消失的也不算——标记不能给一个无法兑现的承诺。判据只有一处实现：
   `mover.has_ab_clip()`。
3. **正交，不改变处置主线。** 档位（`trash_tier`）、处置结论（`human_decision='trash'`）、
   撤销能力（`undo_move` 只认 `trash_path`）全部不变，只是换了个子目录。
4. **存量要单独对齐一次，而且是双向的。** 改 `move_one` 只管得住今后新移动的文件；
   已经在回收目录里的得走一次对齐：`scripts/align_subdirs.py`（默认 dry-run，
   `--apply` 才动手，幂等可重跑；同盘 move 不复制）。工作台「设置与扫描」页的
   「回收目录三堆」卡有同名按钮，同一套判据。**方向是双向的** —— 重剪后新剪出 A/B
   的行要从 `待保全` 挪进 `已剪辑`，所以每跑完一轮重剪都要再对齐一次。
   它是**离线工具**，别和正在跑剪辑的工作台并发（`move_one` 也在搬同一批文件）。

**看产物怎么配对**：产物名以原片名开头（`<原片名>_E01_A_<时刻>_<秒数>s.mp4`），
把原片名复制到精华目录里搜即可。这条路径没有为"检查"额外生成任何文件——
代价是 spot-check 是两步操作。

> 「零产物 / 只有静帧」的重剪入口**不做全量重剪**：队列只收这两类症状
> （`db.rehighlight_queue(only_dropped=True)`，2026-09-13 实测 **1,446 条**）。
>
> 这里早先写过"同素材同参数重剪必然得到同样结果，白烧机时"——**那条已被实测推翻**，
> 见 5.4。产物为空不是"结论"，是当时那版聚合逻辑吃掉了。

### 5.4 hlv3：两处"静默吃掉产物"的聚合规则（2026-09-13）

**症状**：库里 630 条 `highlight_version='hlv2'` 的行，`highlight_clips` 是空的
（或只有静帧），而 `highlight_coarse_hits` 明明 > 0 —— 检出过东西，产物却没了。
因为版本号已是目标值，它们被 `rehighlight_queue` 的 `version <> target` 永久挡在队列外；
回收目录据此把它们判成 `plain`（可直接删）。**其中 489 条此刻正躺在 `G:\need-del` 里。**

**根因是两处规则各把产物扔掉一次**，都在聚合阶段，不在检测阶段：

| 位置 | 做了什么 | 后果 |
|---|---|---|
| `merge_two_levels()` | 「该窗没被精扫到」时还要求**有动静**（`c_diffs > fb_thr`）才降级保留 | "人坐着、只有小动作"被丢第二次 |
| `merge_events()` | `min_duration` 按时长丢弃分组，**不区分纯动静与真实检出** | 孤立单帧检出 ⇒ 组内跨度 0s < 1.0s ⇒ 当"一闪而过的误检"丢掉 |

两处都与自己的**承诺**矛盾：`cut_one()` 里写着"超预算的窗其粗扫检出按疑似保留"，
`min_duration` 的注释写的是"一闪而过，八成是误检"（针对噪点，不是针对检出）。

**修法**：`merge_two_levels()` 去掉"还要求有动静"；`merge_events()` 只在
`all(h["motion_only"])` 时才按时长丢弃。**再 + 把版本号升到 `hlv3`** ——
版本号是本项目唯一的纠偏入口，不给症状谓词加分支（那会自我循环：重剪后仍零产物
⇒ 又被选中），而是"修代码 + bump 版本"：剪完版本跟上即天然幂等。

**同 24 条样本、改前 → 改后**（随机种子固定，同一批 id 直接对比）：

| | 改前 | 改后 |
|---|---:|---:|
| 补出 A/B 产物 | 10 | **10** |
| 只补出 C 档案 | 0 | **9** |
| 仍是零产物 | 14 | **5** |
| 至少留下产物 | 42% | **79%** |

剩下 5 条是**纯动静命中**（没有检出，只有帧差）⇒ 零产物是对的，重剪后它们会回到 `plain`。

**复查入口**：`scripts/audit_highlight.py` —— 按 (症状 × 版本) 分桶列出这类行，
并单独标出「版本已是目标值却仍为空」的可疑行（那才属于"必须修代码 + bump 版本号"的一类）；
`--recut N` 抽样重跑估救回率（只写临时目录，不写库）。**每次动聚合逻辑后都跑一遍** ——
这是唯一能发现"以为修好了、其实还有一层"的尺子（hlv2 就是只修了 `merge_two_levels` 的
已精扫分支、漏了未精扫分支与 `min_duration`，才留下这 630 条）。

> ⚠️ 顺带记一个口径瑕疵：`highlight_coarse_hits` **同时计入 `motion_only` 的动静帧**，

## 六、切割与编码（这里有必踩的坑）

**坑**：监控 H.264 的 GOP 很长。用 `-c copy` 流复制，ffmpeg 只能把切点吸附到
最近关键帧，误差可达数秒，开头还可能花屏/绿帧。监控素材上这个坑是必踩的。

**解法**：每个事件**重编码**切片，换取帧级精确。

```
ffmpeg -ss <start> -i <src> -t <dur> \
  -c:v libx264 -crf 20 -preset veryfast -r 15 \
  -c:a aac -b:a 128k -g 30 -movflags +faststart <out>
```

- `-crf 20`：视觉近无损，体积可控
- `-r 15`：**保持源帧率，绝不升帧**。15fps 素材拔到 30fps 徒增体积且无新信息
- `-g 30`：输出关键帧间隔 2 秒（15fps × 2s），便于拖动预览
- `-movflags +faststart`：边下边播

**输出命名**：`<年份>/<级别>/<源名>_E<序号>_<级别>_<HHMMSS>_<时长>s.mp4`

**同盘是提示，不是限制**：输出目录与源盘/回收盘同盘时给出黄色警告，但**允许执行**——
删除是手动操作，用户清楚自己在删哪个文件夹，决定权留给人。
启动时只拦截真正的硬错误（`is_drive_root`：空目录 / 盘符根目录 / 缺 ffmpeg / 缺模型）。

## 十、运行 SOP

### 日常路径：一键执行（ADR 0004，推荐）

> 决策记录见 `docs/adr/0004-one-click-pipeline.md`。七个阶段原本各一个按钮、
> 散在设置页四个段落和审核台顶部，做一批要上下跑七趟。现在参数配一次、点一下到底。

0. **设置页最上方「⚡ 一键执行」区**
   - ① 路径：源目录 / 回收目录 / 本地工作目录 / 模型 / 语音档案目录 / 精华目录
   - ② 分析参数：目标检测阈值、抽帧数、YOLO 开关
   - ③ 本次要跑什么：本次导入上限（**只限制扫描**）、七个阶段开关（默认全开）
   - 点「⚡ 一键执行（跑完到「回收目录就绪」）」—— 前置条件一次性检查，缺什么直接
     拒绝启动并列出缺什么（不会跑半截）

   链路顺序**由依赖决定**，不可调换：

   ```
   扫描 → AI 分析 → 音频复核 → 语音归档 → 批量放行 → 画面精华剪辑（含自动处置）
        → 回收目录三堆对齐
   ```

   | 约束 | 原因 |
   |---|---|
   | 分析在音频复核/剪辑之前 | 两者的队列都只认已判定的 `trash/review` |
   | 音频复核在语音归档之前 | 归档的数据源是复核产出的转写与缓存 wav |
   | **放行在剪辑之前** | 剪辑的自动处置会搬走未处置候选，而放行队列只认未处置 —— 反序放行就是空操作 |
   | **三堆对齐在剪辑之后** | 对齐按「保全状态」归档，早于剪辑跑会把刚剪出 A/B 的行留在「待保全」里，等于白搬一次 |

   - **只有扫描分批**：上限只管"本次导入多少新料"；其余阶段跑全库队列（都带幂等标记），
     所以点一次会顺带把历史积压一起清掉，第二次点也不会重复劳动
   - **失败语义**：单条坏文件只记录并继续；某阶段整体失败（引擎未就绪/目录非法/抛异常）
     立即停下、不跑下游（上游失败让下游空跑，比停下更危险），面板写清停在哪一步
   - **停止** = 当前文件收尾后不进入下一阶段；**再点一次** = 从断点续跑
   - 跑完 = 回收目录就绪（末尾的三堆对齐会把存量归位，跑完「待归位」应为 0）。
     人只剩两件事：翻「精华复核」页看 A/B 产物、**手动清空回收目录**
     （`已剪辑` / 无精华两堆可直接删，`待保全` 一个都别删）

1. **先跑语音档案归档（L2.7）**（分步执行时的顺序）
   有人声的片段可能还躺在 `G:\need-del` 里。纯文件复制 + 转写，几分钟的事。
   排在精华剪辑之前——它是更确定的收益。

2. **（可选）再跑一次样本验证**
   ```bash
   ./.venv/Scripts/python.exe scripts/_legacy/sample_highlight.py 30
   ```
   改过参数后用来定心，干跑不落库。

3. **全量跑**
   工作台 → 「设置与扫描」→ 🎞 启动画面精华剪辑。
   后台约 2.7 小时，可在「执行进度」页签看进度。

4. **验收**
   「精华复核」页签按 A/B/C 浏览：缩略图 + 真实拍摄时间 + 时长 + 置信度，
   支持直接播放和定位文件。

5. **确认后再清空 `G:\need-del`**
   在此之前，音频已归档、画面精华已留存，可以放心删。

### 审核减负联动（ADR 0001 · 先剪后删，2026-09 定稿）

> 审核台工作量大的根因：人工逐条审原片（曾 1000+/4000 段）。新流程让机器把
> 「剪精华 → 决定去留」一并做完，人只看 A/B 级产物。决策记录见
> `docs/adr/0001-cut-then-delete-replaces-manual-review.md`。

6. **（可选，强烈建议）审核台先一键放行「无人」候选**
   放行候选 = 判删候选里**机器没看到任何人物信号**的片段：未检出人物，且
   `decision_trace` 里也没有"疑似人物未达阈值"（near_miss，漏检高发区）。
   动物/车辆不拦（权重只有人物的三分之一）。人眼盯的缩略图正是机器抽的那十几帧，
   逐条审不产生任何信息。审核台页签顶部会出现「⚡ 审核减负：N 个「无人」片段可
   一键放行」，一键批量移入分级回收目录，之后由精华剪辑 8 倍采样密度兜底重扫。
   分数门槛（`verdict.release_threshold`，默认 30）只作保险丝 —— 判据是人物信号。
7. **音频口径：不拦，靠"事后补"**
   归档/剪辑/音频三个队列都已从「仅已移入回收目录」放宽为**处置候选** = 已移入
   回收目录 OR 未处置的 `trash/review`。所以放行**不必等**音频复核：放行后仍能补
   复核（`review_one` 有 `trash_path` 回落）、补归档，只要**没手清回收目录**。
   代价只有一条：**回收目录被手动清空前，把音频复核 + 语音归档跑完** ——
   一键执行的链路顺序（音频复核先于放行/剪辑）就是为它兜的底。

   > "不拦"说的是**批量放行**（机器路径）—— 它只放"无人物信号"的候选，不看音频。
   > 而**审核台里单条的「确认清理」**对"有音轨且未复核"的片段会**禁用按钮**，
   > 要求勾选"我已人工确认"才放行；自动处置路径（`highlighter._dispose_one`）则无此守卫。
   > 人工路径有明示关口、机器路径靠事后补 —— 两条路径口径不同是**故意的**，
   > 改任一条前先看这里。
8. **精华剪辑剪完自动处置（`highlight.auto_dispose = True`）**
   单条剪完即决策，无需人工介入：
   - 精华占比 > `keep_full_ratio`(0.6) → 自动**整片保留**（切片丢上下文）
   - 已放行（human=trash）但剪出高占比 → 自动**撤销移动捞回**
   - 其余（含确认无精华）→ 自动**移入回收目录**（精华已留底）
   人只在「精华复核」页翻 A/B 产物；任务完成摘要会显示处置统计。

## 十一、风险与边界

1. **低照度漏检**：最大风险。已用 CLAHE + 帧差双路 + 两级检测 + 低阈值四重对冲。
   全量跑完后建议抽看 A 级，据此回调 `coarse_conf`。
2. **误检**：低照度噪点、衣架、拖把可能被当人。C 级=档案不是待办，代价可控
   （C 级不进审核队列；hlv2 起 C 段也切 mp4，占用见第九节的磁盘约束）。

   **"换个更大的 YOLO"这条路已经实测否定**（2026-09-12，同一批 20 条已目视标注的 A/B
   产物，输入尺寸都对齐到 640，只换模型）：

   | 指标 | yolov8n@640 | yolov8s@640 | yolov8n@1280 |
   |---|---|---|---|
   | 误检组仍被报出 person | 3/6 | **4/6** | 3/6 |
   | 真人组被报出 person | 3/5 | 3/5 | 3/5 |
   | 误检组最高 conf | 0.45 | **0.75** | 0.61 |

   大模型不但没压住误检，反而**让误检更自信**（0.45→0.75），而真阳性一条都没多。
   把输入从 640 抬到 1280 同样无效（误检 3/6 不变）。样本只有 6 条误检，
   "3→4" 这一步不构成统计显著；但 conf 被整体抬高是方向性证据，且与机理一致：
   更大的 COCO 模型学到的语义更像"红袋子在 COCO 里也是 person"。
   ⇒ 换更大的同族模型**不是**这个问题的解。

   结论可复核：`scripts/compare_models.py`（按**标注时的 id 原样取行**，不重新抽样
   —— 库一直被工作台改写，重抽会导致标签对不上；每个模型显式带输入尺寸）。
   网络恢复后加 `--extra yolo11s yolo11m` 可把 yolo11 那一档补上。

   **换模型前必须先过两道门**（实测各踩一次）：
   - **官方 `yolov8s.onnx` 是静态 640**：喂 1280 直接崩在
     `dnn/src/layers/reshape2_layer.cpp` 的 `outTotal == inpTotal`。
     精扫档（`fine_size=1280`）会整段挂掉。要换任何模型，先确认它**支持动态输入**。
   - **ONNX 未必能被 OpenCV DNN 加载**：`yolo11s.onnx`（官方 v8.4.0）在 OpenCV 5.0.0
     上**装载即失败**（onnx importer 报错），根本进不到推理。
     `scripts/download_model.py` 的 `verify()` 原来只试 640，
     两道门都测不到 —— 现已补上 1280 与"装载"两项检查。

   剩下可走的方向（都还没验证）：**换不同架构/专门的人体检测器**（而不是更大的 YOLO）、
   或走"机器宁可多留、人工 3 秒剪刀"——给「精华复核」页每条产物加一个
   "❌ 不是人" 否决入口。
3. **切割精度**：必须重编码，不能 `-c copy`（见第六节）。
4. **算力**：全量约 2.7 小时，纯 CPU。中途可停，已完成的不重跑（幂等）。
5. **隐私**：全程本地处理，不上传任何云端服务。素材含家庭生活影像，这点写死。
6. **15fps 低帧率**：输出保持 15fps。慢动作需要 60fps 源，本素材不具备条件。

## 十二、后续可扩展（当前不做，留接口）

- **人脸识别聚类**（insightface）：按家人分组，一键生成"某人的年度合集"
