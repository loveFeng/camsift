# 把六步流程串成「一键执行」

---
status: accepted
date: 2026-09-10
---

扫描、分析、音频复核、语音归档、画面精华剪辑、批量放行原本各自一个按钮，
散在设置页四个段落和审核台顶部。做一批素材要在页面上上下下跑六趟，且每趟都可能
忘在某个页签里。决定：在设置页置顶一个「一键执行」区 —— 参数一次配好，点一下依次跑完，
终点是"回收目录就绪，只剩机主手动删除"。

## 链路顺序由依赖决定

```
扫描 → 分析 → 音频复核 → 语音归档 → 批量放行 → 画面精华剪辑（含自动处置）
```

- **分析在音频复核/剪辑之前** —— 两者的队列都只认已判定的 `trash/review`。
- **音频复核在语音归档之前** —— 归档的数据源是复核产出的转写与缓存 wav。
- **放行在剪辑之前** —— 这条最反直觉，但反序会让放行失效：剪辑的自动处置会把
  未处置候选全部搬走，而放行队列只认未处置，排在后面就是空操作。
  ADR 0001 的原话也正是"**放行后**由画面精华剪辑用 8 倍采样密度兜底重扫"。

## Decision 细节

- **下游跑全库队列，只有扫描按上限分批。** 扫描限额控制"本次导入多少新料"
  （IO 密集、会撑大数据库），而分析/音频/归档/剪辑/放行都是带幂等标记的队列
  （`status`/`audio_checked`/`archived_at`/`highlight_at`），跑全库天然把历史积压
  一起清掉，且不会重复劳动。第二次点会顺带把新扫的一起带上。
- **六个阶段都可单独勾掉，默认全开。**
- **阶段级失败即停，单条失败继续。** 单条坏文件只记录；引擎未就绪/目录非法/抛异常
  这类阶段级失败立即停下，不跑下游，面板写清"停在哪一步、为什么"。
- **前置条件在点按钮时一次性检查**（源目录、work_dir、trash_root、ASR 引擎、
  ffmpeg、归档目录、精华目录），缺一个就拒绝启动并列出缺什么。
- **停止 = 停整条链**（当前文件处理完收尾，不进入下一阶段）；**再点一次 = 从断点续跑**。
- **检出人物的 review 片段也一并自动移入回收。** "每一帧 L1 确认的人仍有人看"
  由 A/B 精华产物兑现（在「精华复核」页看），不再回到原片。

## Considered options

- **维持六个独立按钮** —— 否掉：这正是要被取代的现状。
- **严格本批（下游也限定本次扫描的批次）** —— 否掉：历史积压（批次 7/8 的 1604 条
  待剪辑 + 880 条待放行）永远碰不到，得另外点，与"点一次做完"直接矛盾。
- **失败继续（尽力而为，逐阶段跳过）** —— 否掉：上游失败会让下游空跑或半成品，
  面板却显示"做完了"。例：音频复核全挂 → 剪辑的守卫拦住所有有音轨的候选 →
  回收目录是空的，但用户以为已完成。比停下来更危险。
- **检出人物的留给人工在审核台看原片** —— 否掉：与 ADR 0001「先剪后删」冲突
  （先剪后删的全部意义就是人不再审原片），且精华产物已保留人像帧。
- **把参数散着保留、只加一个大按钮** —— 否掉：用户要的是"先设置完，再执行"，
  参数仍要在页面上上下下找就不算完成。

## Consequences

- **`审核` 的适用范围缩小了。** 一键执行跑完，审核台通常是空的；
  人的剩余工作是"翻 **画面精华** 产物 + 手动清空回收目录"。
- **一键执行必须是一个可观察的长任务**：一次可能是几小时到一整晚。
  面板要显示"当前阶段 N/6 + 阶段进度"，关掉浏览器不中断（沿用现有 JobManager
  的进程级单例 + 后台线程）。
- **`_run_analyze` 丢失 `batch_id` 不再是缺陷** —— 按全库队列口径它本来就该跑全库。
  但若将来要做"严格本批"，这个参数必须补回来（`Analyzer.run` 已支持 `batch_id`）。
- **放行的安全性完全依赖 ADR 0003 的语义条件 + 剪辑兜底**：回收目录被手动清空之前，
  原片都还在，可撤销、可精扫捞回。
- **待消解项**：`move_all`（人工一键放行）没有音频守卫，而 `_dispose_one`
  （剪辑后自动移入）有。两条路径口径不一致 —— 语义条件化之后，"拦住"与"事后补"
  是两种手段，不能一半拦一半不拦。本 ADR 的链路顺序（音频复核先于放行）让这个问题
  在**流水线内**不再触发，但手动路径仍然暴露。
