# 精华剪辑的定位是「删除前的最后保全」：粗扫疑似不丢弃、C 级也切 mp4

---
status: accepted
date: 2026-09-10
---

机主明确定义了评价标准：**"我是想将需要删除的视频更好的做一下精华剪辑，因为删除后
就再也找不到了。"** 这句话把精华剪辑从"省得人多看一眼"的附属品，改成了
**原片被手动删除之前的最后一道保全**（音频侧由语音档案负责）。评价指标随之从
"准确率"换成 **"召回率 + 覆盖面"**。

## 决定

1. **整片静止 = 无人。** 帧差预筛判定整片无变化时，不再另设"盲区补检"去重扫
   （原 Track B 取消）。代价可接受，算力留给更有收益的地方。
2. **粗扫疑似不再丢弃。** 粗扫（640/0.15）看到目标、精扫（1280/0.25）没确认时，
   降级保留为 C 级疑似（`level=LV_SUSPECT`），而不是按旧口径直接丢弃。
   开关 `highlight.keep_coarse_suspect`，落点 `highlighter.merge_two_levels()`。
3. **C 级也切可播放 mp4。** 从"只留一张静帧"改为"切 mp4 + 3 张代表帧"。
   开关 `highlight.c_cut_mp4` / `highlight.c_thumbs`。
4. **C 级是档案，不是待办。** C 级不进人工审核队列（审核队列仍只认 A/B），
   所以"多留"不等于"多看"。落点 `db._review_sql(hide_c_archive=)` +
   审核台「含仅 C 级档案」开关。
   > ⚠️ 该开关的宿主（审核台）已于 2026-10-05 随 [ADR 0007](0007-spotcheck-driven-auto-dispose.md)
   > 退役；`hide_c_archive` 参数与 `db` 层判据仍保留（抽查页与精华复核页在用）。
5. **L1 提精度用多帧一致性，不是抬阈值。** 真人移动会连续多帧命中，杂物误报多为
   单帧闪烁；抬阈值会把"只在一两帧出现、conf 0.3–0.4 的真人"一起干掉。
   硬指标：**真人漏检增量 = 0**。方向已定，阈值参数由 P4 校准报告定
   （见 `开发计划-删除前精华保全.md`）。

> Track A（第 5 条）与 Track C（第 2–4 条）**必须同批上线**：L1 收紧会把更多视频
> 推进"待删除"，也就更依赖 L2 兜底。只做 A 不做 C，等于把安全网收紧的同时
> 提高了坠落概率。

## 为什么旧口径是错的

旧行为把"精扫没确认"当成"没有"。在低照度素材上这个推断不成立 —— 实测**同一帧**
粗扫给 0.42、精扫给 0.19（高分辨率把低对比 / 小目标的置信度压低）。于是：

- **D2**：一条视频的粗扫检出若全被这样丢弃，`hits` 为空 ⇒ 判"无精华" ⇒
  自动移入回收目录。实测 **474 条视频"粗扫明明看到过东西、最终零产物"**，
  删除后一个字都不会留下。
- **D3**：`C 级 = 低置信度疑似 或 纯动静` 这一定义里，前半支**结构性永不成立** ——
  476 个 C 全部是纯动静（conf=0），"看到过但不敢确认"的信号一条都没留。

删除不可逆，多留只是多占空间。**两者代价不对等**，所以唯一正确的偏置是宁可多留。

## Considered options

- **全库降阈值 / 全量加密检测** —— 否掉：算力 14–54 倍，而且前提是"漏检"，
  而抽查证明这批是**误报而非漏检**（成本 / 覆盖率实测见归档的 v1 计划 §8）。
- **提高粗扫阈值以减少误报** —— 否掉：方向反了。误报的代价是被精扫过滤（多花算力），
  漏检的代价是家庭影像永久消失。
- **C 级继续只留静帧（省空间）** —— 否掉：静帧只能证明"某一秒有过东西"，
  而"删除后再也找不到"要的是能回放的整段。C 级不进审核队列，多留不会变成多看。
- **引入 VLM 做二次复核** —— 否掉：慢 100–1000 倍，性价比远不如"高密度重扫"。
- **L1 直接抬 `yolo_conf_threshold`** —— 否掉：会把只在少数帧出现的真人一并干掉，
  改用多帧一致性（第 5 条）。

## Consequences

- **新增产物上界约 15GB**（当时 G 盘仅剩 71G）——三个开关
  （`keep_coarse_suspect` / `c_cut_mp4` / `c_thumbs`）可一键退回旧行为。
- **「无精华」必须可解释**：拆成"已检测确实没有 / 预筛跳过 / 粗扫看到但被否决"三义
  （`db.no_clip_breakdown()`），否则看不出保全到底有没有生效。
- **产物口径需要版本化**：`highlight.version`（`hlv1` → `hlv2`）+
  `db.rehighlight_queue()` 让**存量按新口径重剪**（幂等、可中断）。否则代码改了、
  已剪的 4,825 条仍是旧口径。`highlight_clips` 每段带 `ver` 字段。
- **存量重剪完成前不得手动清空回收目录** —— 源文件一旦被删，重剪无从执行。
- **本 ADR 不改变**"程序只移动、不删除；删除始终由机主手动完成"这条红线。
