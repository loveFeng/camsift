# 数据模型

> **状态：现行** ｜ 单一 SQLite 库（`runtime.sqlite_path`，默认 `data/videos.db`）。
> 字段真源 = `src/db.py` 的 `SCHEMA` + 三张迁移常量表；**列数别照本文抄，改字段先看代码**。
> 队列谓词真源 = `src/db.py` 的 `Database.*_queue()` 方法。

## 三、问题三义的尺子（`Track 0`）

`no_clip_breakdown()` 把「无精华」拆成**互斥**的四义 —— 没有它们，"无精华 N 条"里分不出
"真复核过没有"和"压根没跑检测"，而后者曾把"粗扫明明看到过目标"的视频静悄悄推进回收目录：

| 分义 | 判据 | 含义 |
|---|---|---|
| `detected_empty` | `highlight_sent > 0` 且 `coarse_hits = 0` | 跑过检测，确实没有 |
| `skipped` | `highlight_sent = 0` | 帧差预筛判定整片静止，YOLO 一帧没跑（**已接受的口径**） |
| **`dropped`** | `highlight_sent > 0` 且 `coarse_hits > 0` | 粗扫看到过，最终零产物 ← **静默漏检，最贵的一类** |
| `unknown` | `highlight_sent IS NULL` | 回填前的历史行 |

四者之和必须等于无精华总数（`selftest` 有断言）。`sent IS NULL` 只能落进 `unknown`，
**不能**因为 `COALESCE(NULL,0)=0` 同时被算成"预筛跳过"（曾因此重复计数）。

## 四、队列谓词总表 ⭐

**这是本模型最容易出事的地方** —— 计数方法与队列方法口径一旦不一致，UI 就会报"待办 0 条"而实际几千条。

### 4.1 两个基础谓词

```sql
-- 处置候选（_PENDING_OR_TRASHED）：凡"要删"的都在内
(human_decision='trash' AND trash_path IS NOT NULL)
OR (human_decision IS NULL AND verdict IN ('trash','review') AND meta_ok=1)
```

```sql
-- 审核队列底座
verdict IN ('trash','review') AND meta_ok=1
```

### 4.2 各队列

| 队列 | 方法 | 谓词 | 幂等标记 |
|---|---|---|---|
| 审核 | `review_queue` / `count_review_queue` / `count_review_below` | 审核底座 + `human_decision IS NULL` + 筛子 | 处置即退出 |
| 音频复核 | `audio_review_queue` / `count_audio_pending` | **处置候选** + `has_audio=1 AND audio_checked IS NULL` | `audio_checked` |
| 语音档案 | `archive_queue` / `count_archive_pending` | **处置候选** + `speech_present=1 AND archived_at IS NULL` | `archived_at` |
| 画面精华 | `highlight_queue` / `count_highlight_pending` | **处置候选** + `highlight_at IS NULL AND highlight_error IS NULL` | `highlight_at` |
| 重剪 | `rehighlight_queue` / `count_rehighlight_pending` | `highlight_at IS NOT NULL AND highlight_error IS NULL AND COALESCE(highlight_version,'hlv1') <> 目标版本`，可再按症状收窄 | 版本号 |
| 放行 | `release_queue` / `count_release` | 审核底座 + `human_decision IS NULL` + `分数 <= release_threshold` + `has_person=0` + **`decision_trace` 里无 `near_miss.person`** | 处置即退出 |

**四条必须记住的口径规则**：

1. **队列方法是唯一真源**。审核队列的谓词集中在 `_review_sql()` 一处，队列 / 计数 / 分数跳转定位
   三者共用 —— 否则"显示 1000 条但翻两页就空"会反复出现（`count_audio_pending` 踩过：计数与队列不一致，报 0 实际 2322）。
2. **`A OR B` 必须整体加括号**。`谓词 SQL` 本身是 `A OR B`，若写成
   `WHERE (A OR B) AND 过滤` 漏掉外层括号，AND 只约束 B、A 分支绕过过滤
   —— 真事故：已移入回收的视频绕过 `highlight_at` 过滤，每次批处理都重剪。
3. **`scope` 只作用于"未处置"那一半**（`_pending_or_trashed_sql`）。已处置行的 `verdict` 仍是 AI 当初的判定，
   放行不会改写它；整条谓词都用 verdict 过滤会让放行过的 review 档从音频队列里漏掉。
4. **队列看不见文件系统**。归档队列的门是 `speech_present=1` 而不是"wav 存在"，剪辑队列同理 ——
   所以凡是"某条件下跳过"的规则，都必须体现在**列**上（如 `audio_checked`），否则会出现
   "进队列 → 被跳过 → 又留在队列里"，UI 永远归不了零。

### 4.3 「待保全」= 两条队列 ∪ 硬失败行

`mover.is_pending()` 的行内判据与队列**在"回收目录"这个域上等价**，它比队列多包含一类：
**硬失败行**（`highlight_error` 非空）—— 队列把这类排除（重试也没用），但对"这条原片能不能删"来说
它们和排队中的行一样是**没保全**的，必须算待保全。

> ⚠️ 这个判据**不能拿去筛全库**。实测 `human_decision='keep'` 的行里有相当一部分"从未剪过"，
> 行内判断说"待保全"、队列说"不在队里"。两处发散是**刻意不修**的：`keep` 是人工已经表过态的行，
> "还没剪完"对它没有意义（`highlighter._dispose_one` 见到 keep 返回 `not_disposed`，不会把它移回回收目录）。

## 五、状态与不变量

| 字段 | 取值 | 流转 |
|---|---|---|
| `status` | `pending` → `metadata` → `analyzed` → `keep` / `trash`；探测失败为 `error` | 常量 `STATUS_*` |
| `verdict` | `keep` / `trash` / `review` | 由 `analyzer.build_decision()` 写一次 |
| `human_decision` | `NULL` / `trash` / `keep` | 只由人工审核或批量放行 / 剪辑自动处置写 |

**不变量**：

- `human_decision='keep'` ⇒ `trash_path IS NULL AND trash_tier IS NULL`（`set_human_decision` 直写不继承）
- `meta_ok=1` 才可能进任何下游队列
- `highlight_error` 非空 ⇒ 不在两条剪辑队列里（但仍在「待保全」的语义内）

## 六、产出口径版本号：三个真源必须同时改 ⚠️

目标版本 = **`hlv3`**（`hlv1` 旧 / `hlv2` 删前保全 / `hlv3` 检出必留）。

| # | 位置 | 谁读它 |
|---|---|---|
| 1 | `config.json` 的 `highlight.version` | **剪辑器实际写库的值** |
| 2 | `highlighter.HL_VERSION` | 剪辑器的默认/回退值 |
| 3 | `db.HIGHLIGHT_TARGET_VERSION` | `rehighlight_queue` 的默认目标 + **`mover` 直接 import 它** |

`scripts/selftest.py::test_hl_version_single_source` 断言三处相等。

**漂移是单向且不可见的**：`config` 比 `db` 新 ⇒ 每条新剪的行都被判成"版本落后 ⇒ 待保全"，
**回收目录永远不会归零**；反过来 ⇒ 该重剪的不重剪。

**版本号是唯一的纠偏入口**：发现某版口径曾静默吃掉产物时，正确做法是
**修代码 + bump 版本号**，而不是给队列加症状分支 —— 症状分支会自我循环
（重剪后仍零产物 ⇒ 又被选中），bump 版本天生幂等。改完跑 `scripts/audit_highlight.py`
（症状 × 版本分桶，专挑"版本已是目标值却产物为空"的可疑行）。

## 七、访问口径（踩过的坑）

| 坑 | 规则 |
|---|---|
| `sqlite3.Row` | 只支持 `row["x"]`，**没有 `.get()`** → 先 `row = dict(row)` |
| 大 JSON 列 | 队列 / 统计查询**绝不 `SELECT *`**：`raw_detections` / 转写 / `highlight_clips` 能把内存吃满。只取需要的列（`cols=` 参数就是为此存在） |
| 批量路径的性能 | 批量判「待保全」要传 `db.pending_highlight_ids()` 一次性算好的集合；单条路径（`move_one`）才回落到行内判断 |
| 写库与写 manifest | 批处理循环里**两者都要包在 try 内**：异常冒出循环会炸掉整批且不进 except ⇒ `*_error` 一条不记，表面"零失败"实际整批挂了 |
| 物理删除 | `Database` **不提供任何删除接口**（红线） |

## 八、只读复现

```bash
# 四条诉求对现库实数（mode=ro，不写库不动作）
./.venv/Scripts/python.exe scripts/audit_requirements.py

# 精华产物体检（症状 × 版本分桶）
./.venv/Scripts/python.exe scripts/audit_highlight.py
```

`audit_highlight.py --recut N` 只把产物切到临时目录，不写库、不碰回收目录。
