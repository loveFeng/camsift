## 一、P0 · 会丢东西或会停摆

### 1. 新口径（`hlv3`）重剪一次都没跑 ⇒ 「待保全」无法归零

`hlv3` 已写进 `config.json`、代码已修（聚合阶段的静默丢件），但**历史行还停在 `hlv1/hlv2`**，
所以重剪队列里压着一批行、`待保全` 子档也就不会清零。

- **为什么贵**：`待保全` 归零 ⇔ 可以放心手动清空回收目录。不跑完就清，等于把"还没落袋的精华"删掉。
- **动作**：重启工作台 → 点「重置失败记录」清硬失败行 → 跑「按新口径重剪」→ 再跑「对齐子档」。
- **验收**：`待保全` = 0；`scripts/audit_highlight.py` 里"版本已是目标值却产物为空"的那一桶 = 0。
- **别写死条数**：批次大小是活的，执行前看 UI 按钮或 `db.count_rehighlight_pending(only_dropped=True)`。

### 2. `data` 根路径分裂成两条 ⇒ 删错一棵树就停摆

| 用途 | 现网路径 | 内容 |
|---|---|---|
| `runtime.sqlite_path` + `config.ROOT/data`（thumbs/models/probe） | `E:\code\video-search\data` | **数据库、缩略图** |
| `work_dir` / `yolo_model_path` / `audio.model_dir` | **`E:\video-search\data`（旧树）** | **音频复核缓存 wav**、YOLO 模型、抽帧残留 |

- **为什么贵**：`yolo_model_path` **只**指向旧树。删掉这个"看起来像残留"的目录 ⇒ `check_ready` 报
  "未找到 YOLO 模型"，**L1 与 L2.8 全线停摆**（新树里那份副本配置根本没指向）。20 GB 级音频缓存也躺在那儿，没人知道。
- **动作**：把 `work_dir` / `yolo_model_path` / `audio.model_dir` 统一改到 `E:\code\video-search\data`，
  迁移音频缓存后**再**清旧树。**顺序不能反**。
- **验收**：改完跑 `启动工作台.bat`，`check_ready` 无告警；`scripts/selftest.py` 全绿；L1 与 L2.8 各跑一条。

### 3. 产物与回收目录**同盘** ⇒ "腾空间"时容易一起清掉

`config.json` 里 `archive.dir = G:\change\audio`、`highlight.dir = G:\change\video-highlights`，
而 `trash_root = G:\need-del`、源片在 `G:\change\20xx` —— **同一块盘、同一个父目录**。
源码注释里明写着红线"`archive.dir` 绝不能设在源盘/回收盘所在的盘"，**现网配置恰好违反了它**。

- **为什么贵**：机会窗口一关就是永久 —— 顺手清 `G:\change` 会把音档和精华一起带走。
- **动作**（择一）：把两个产出目录移到别的盘（改 2 行配置 + 搬一次目录）；或至少**永远不要整目录清 `G:\change`**。
- **注意**：搬之前先做 C5（manifest 相对路径化，见 P2），否则 manifest 的 `wav`/`txt` 字段会静默失效。

### 4. 顺序红线：清空回收目录**必须**晚于「音频复核 + 归档」（不可逆）

语音档案吃的是**音频复核的缓存 wav**，不是视频本体。在复核跑完前清空回收目录，未复核行里的有效语音就真丢了。

- 一键执行已按 **复核 → 归档 → 放行 → 剪辑** 排序（ADR 0004）；单独点按钮时也必须守这个顺序。
- **验收**：`scripts/audit_requirements.py` 的 ④ 段两个告警项归零。

## 二、机主运维顺序（唯一硬期限在第 4 步）

```
① 停止服务.bat → 启动工作台.bat          ← 改了 src/ 必须重启（Streamlit 模块缓存跨 rerun 保留）
② 点「重置失败记录」                     清掉硬失败行，让它们回到队列
③ 跑「按新口径重剪」（hlv3）             小时级，可中断续跑
④ 跑「音频复核」→「语音档案归档」          ★ 必须早于第 6 步 —— 归档吃缓存 wav，不可逆
⑤ 跑「对齐子档」                         把新剪出 A/B 的原片从「待保全」挪进「已剪辑」（幂等）
⑥ 确认「待保全」= 0 后，才手动清空回收目录
⑦ 之后把 G:\change\audio 整体搬到专用盘
```

## 四、P2 · 可选 / 优化（都不阻塞）

| # | 事项 | 判断 |
|---|---|---|
| 11 | **C5 · `manifest.jsonl` 相对路径化** | 搬盘会让 `wav`/`txt` 字段静默失效。改 2 行、当前无代码读它。**要做 C3（搬产物）就先做它** |
| 12 | 抽帧落盘再读回 ⇒ 改管道 | `highlighter._extract` 写 jpg 再 `cv2.imread`，改 `image2pipe` 直接进内存可省一块磁盘 IO（占比未 profiling，属推断） |
| 13 | 推理批量化 | 逐帧单次调 YOLO ONNX；ONNX Runtime 支持 batch，纯 CPU 环境下最直接的提速点（幅度未实测） |
| 14 | `count_release()` 全量拉内存 | 每次渲染都把候选行的 `decision_trace`（大 JSON）拉进 Python 判 `near_miss`。库涨大后建议把 `near_miss` 规范化成一列 |
| 15 | 放行没有分批护栏 | `_run_release` 一次 `move_all` 全部候选，没有 `batch_size_limit` 之类的护栏。量级上去后单次搬几万个文件风险偏高 |
| 16 | `highlight_count` 与 `highlight_sec` 口径不同 | `count = len(clips)`（含只有静帧的 C 段），`sec = sum(dur for c in clips if c["file"])`（不含）。新口径下 C 级也切 mp4，所以分歧只在"切段失败"的行上出现 |
| 17 | 一键执行是单线程串行长跑 | 扫描（磁盘 IO）/ 检测（CPU 推理）/ 编解码（CPU）是三类资源，串起来跑浪费。规模大时值得做"检测与切割分离的两级流水" |
| 18 | 归档产物有重复副本 | `mark_archived` 在写 manifest **之后**调用 ⇒ 进程被杀会留"文件已写、标记未写"的窗口，重跑以 `_<id>` 后缀再复制一份。**不是活 bug**（`archived_at` 挡得住），但**清了 `archived_at` 重跑会翻一倍**。无害，暂不清理 |
| 19 | 归档格式 16 kHz PCM（可选转 opus） | 产物约 256 kbps 而源音频仅 ~28 kbps ⇒ 确有约 9 倍空间。但收益不抵"归档 = 原样留存"这个简单心智模型被破坏的代价 |
