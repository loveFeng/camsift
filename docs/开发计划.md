## 0. 相对初始需求的关键修正

原始方案有 5 处需要修正，其中第 1 条会直接决定项目成败。

| # | 原方案 | 问题 | v2 修正 |
|---|--------|------|---------|
| 1 | 判定"无人 + 无声 + 无动静" | **"无动静"在移动侦测场景下恒为假**，AND 进去后筛不出任何东西 | 改为判定"**无目标对象**"（无人/无车/无关注物体），动静只用于刻画"误触发指纹" |
| 2 | 一次性处理 10TB | 工期不可控，按单线程解码需数月 | **分批处理**，批次可中断续跑，边跑边审 |
| 3 | 主攻 YOLO 推理优化 | 瓶颈搞错了：YOLO 抽帧仅 ~0.2s，H.265 解码要 5-20s | 优化**解码环节**：关键帧抽帧 / GPU 硬解 |
| 4 | 布尔 AND 硬阈值 | 无法排序，人工审核不能优先看最可疑的 | 改为**保留价值分**，按分数升序审核 |
| 5 | 直接 `shutil.move` 到扁平回收目录 | 监控片段命名高度重复，几十万文件必然撞名覆盖 | 回收时**保留原目录结构** + 操作日志 + 可撤销 |

**规模重估**（分批后不再是阻塞项）：1080p H.265 移动侦测录像，码率 1-2 Mbps，10TB ≈ 1.1万~2.2万小时。若片段平均 1-3 分钟，总量约 **20万~130万 个片段**。分批后每批处理 100-500GB，节奏可控。

## 0.5 场景硬约束（2026-09-03 更新）

用户补充了三条决定性信息，它们**重新排列了方案的优先级**：

| 事实 | 影响 |
|------|------|
| 数据已拷至 **USB 机械移动硬盘**，**按年份分目录** | ① 年份目录 = 天然批次单位，分批策略直接确定<br>② USB 机械盘顺序读 100-130 MB/s，**10TB 纯顺序读即需 25-28 小时**，IO 升为第一约束 |
| **唯一一份，原件已无** | 风险等级拉满 —— 见 0.5.1 |
| **所有年份同等重要** | 不适用"老年份整批归档"的捷径，走完整方案；年份**仅作分批单位** |

### 0.5.1 ⚠️ 空间释放悖论（必须先想清楚）

这是本项目**最核心的矛盾**：

- 目标是"清理出空间" → 必须 **delete**
- 但数据唯一 → delete **不可逆**
- 跨盘 move 到本机 = 复制 10TB（USB 上几十小时，且需要第二块盘）
- 同盘 move 到回收目录 = 瞬间重命名、完全可撤销，**但一个字节都不释放**

**程序边界（已明确）**：

| 阶段 | 谁做 | 性质 |
|------|------|------|
| ① 分析、打分、排序 | **程序** | 只读 |
| ② 移入分级回收目录 | **程序** | 可撤销 |
| ③ 真删释放空间 | **用户手动** | 不可逆 |

> **程序永不执行 delete / format 或任何不可逆操作。** 分工是对的：程序只负责把「该删什么」回答清楚，并把文件整理到方便手动处理的位置，最终拍板权在人手里。

> 注意：**在用户手动删除前，磁盘空间不会减少**（文件只是换了目录）。这是"数据唯一"必须付出的代价。

**备份建议依然成立**（见 0.5.2）：程序不删除只是把"误操作"的风险降到零，但降不了"硬盘本身挂掉"的风险。

### 0.5.2 强烈建议：先买一块盘做备份

**这是投入产出比最高的一件事**（10TB 机械盘约 1000-1500 元，在 5000 元预算内）。理由：

1. 这是**唯一能真正消除"唯一一份"风险**的手段，任何软件方案都替代不了
2. 顺带解决 IO 问题：备份盘若接 SATA / 高速接口，分析速度比 USB 快数倍
3. 有了备份，才敢真删、才谈得上真正释放空间
4. 额外收益 —— 可以反过来做**选择性备份**：只把"要保留的"复制到新盘，确认无误后清空原盘。复制失败不影响源数据，**比删除安全得多**

> 现状本身就是风险：10TB 唯一数据存放在一块需要长时间连续读写的 USB 机械盘上。**在讨论怎么删之前，先讨论怎么保住它。**

### 0.5.3 USB 机械盘的 IO 策略

| 原则 | 做法 |
|------|------|
| **只读分析，产物外置** | 移动硬盘只承受 1 次顺序读；数据库、缩略图、日志**全部写本地 SSD** |
| **必须 GPU 硬解** | CPU 软解会让总耗时从 ~30 小时膨胀到数百小时，USB 盘扛不住这么长的连续负载 |
| **按年份分批 + 断点续跑** | 连续跑 25+ 小时有掉盘 / 过热风险；每批之间停歇，状态落库随时可续 |
| **先试点一个年份** | 拿单一年份跑通全流程 + 校准阈值，再推及其他年份 |

**产物绝不能写在移动硬盘上**：分析过程的随机写会拖垮 USB 盘；且一旦掉盘，几天的分析结果会跟着一起丢。

## 1. 需求定义

### 1.1 目标

识别并整理出**移动侦测误触发产生的无效录像**，移入分级回收目录，为用户手动释放空间提供决策依据。

**程序职责边界（重要）**

| | 程序 | 用户 |
|---|------|------|
| 分析、打分、排序 | 做 | — |
| 移入分级回收目录 | 做 | — |
| **删除释放空间** | **从不做** | **手动** |

程序交付的是一份"该删什么"的清单 + 整理好的分级目录，**不替用户做最终决定**。所有不可逆操作的决策权保留在人手里。

### 1.2 场景特征（决定了方案设计）

- 摄像头**固定机位**，视角不变 → 可以用**背景建模**（MOG2），比简单帧差鲁棒得多
- 录像由**移动侦测触发** → 每个文件天然"有动静"，动静本身不是判别特征
- **大部分视频是有用的** → 这是个低召回率的清理任务，**宁可多留，不可误删**

### 1.3 判定逻辑重构：从"三无"到"误触发识别"

**核心命题**：录像确实动了 —— 但动的是什么？

| 触发源 | 是否保留 | 识别方式 |
|--------|---------|---------|
| 人经过 / 停留 | **保留** | YOLO 检出 `person` |
| 车辆经过 / 停放 | **保留** | YOLO 检出 `car/truck/bus/motorcycle/bicycle` |
| 动物（猫狗鸟） | 可配置 | YOLO 检出 `cat/dog/bird`，默认降级为"可疑" |
| 树叶晃动、光影变化 | **清理** | 无目标检出 + 前景面积小 / 位置固定 / 周期性摆动 |
| 车灯扫过、开灯关灯 | **清理** | 无目标检出 + 全画面亮度突变 |
| 下雨、下雪、飞虫 | **清理** | 无目标检出 + 高频细碎前景 |
| 摄像头噪点 / PTZ 自转动 | **清理** | 无目标检出 + 全画面位移 |

**结论**：v1 的主干判定只看一件事 —— **画面里有没有"关注目标"**（默认人 + 车）。动静类指标作为 v2 增强，用于细分误触发类型。

### 1.4 非目标（明确不做）

- **不做删除**：`delete` / `rmtree` / `unlink` 等不可逆操作一律不实现，最终删除由用户手动完成
- 不做人脸识别 / 车牌识别（超出需求，且精度要求远超当前算力预算）
- 不做实时分析（这是离线批处理任务）
- 不做视频转码归档（只做筛选与移动，不改编码）

## 2. 【最高优先级】Phase -1：先确认 NVR 能不能直接给出答案

**在做任何 AI 之前，先花 1 小时确认这件事** —— 它可能让整个项目从"几周的 AI 工程"降级为"一个脚本"。

多数现代 NVR / 摄像头（海康、大华、宇视、Reolink）本身就在做**人形检测 / 车辆检测 / 移动侦测**，并且：

- 录像文件的**命名或伴生元数据**里可能就带事件类型
- NVR 通常支持**导出事件日志**（CSV / SDK / ONVIF 事件订阅）
- 部分 NVR 会把事件标记写进视频的私有数据块

**如果能拿到 NVR 的事件日志**：直接筛选"触发类型为移动侦测、但**无人形/无车辆**"的事件 → 准确率接近 100%，且**完全不需要解码视频**，10TB 的处理时间从数周降到几分钟。

**探测动作**：
1. 确认 NVR 型号与固件版本
2. 在 NVR 界面查：事件/报警日志能否导出？能否按"人形检测"筛选？
3. 抽查几个录像文件的命名规则，是否含事件类型字段
4. 抽查 NVR 数据库文件（通常在录像盘根目录，如 `index.db` / `*.idx`），能否直接读取

**决策分叉**：
- ✅ NVR 有事件数据 → 走**轻量路线**，跳过 Phase 2 的 YOLO，直接进 Phase 4
- ❌ NVR 无可用数据 → 走**完整路线**，从 Phase 0 开始

## 3. 关键设计决策

### 3.1 分批处理：以年份目录为批次单位

```
批次定义：年份目录（数据已按年分目录，天然批次单位；单年过大时按月份子目录细分）
批次顺序：先挑一个年份做试点，跑通全流程 + 校准阈值后再推及其他年份
状态持久化：每个文件的分析状态写库，随时 Ctrl-C，随时续跑
产物位置：数据库 / 缩略图 / 日志一律写本地 SSD，移动硬盘全程只读
```

理由：10TB 在 USB 机械盘上纯顺序读就需 25-28 小时，一次跑完不现实且有过热掉盘风险。分批后可以**边跑边审边回收**，第一天就有产出，且能根据首批效果及时调整阈值。

### 3.2 解码策略（真正的瓶颈）

**禁止**逐个视频完整解码。采用三级策略，按环境自动降级：

| 优先级 | 方案 | 单片段耗时 | 说明 |
|--------|------|-----------|------|
| 1 | GPU 硬解（`h264_cuvid` / `hevc_cuvid`）+ 抽帧 | ~0.3s | 有 N 卡时首选，快 10-30 倍 |
| 2 | CPU `-ss` seek + 只解关键帧（I帧） | ~1-2s | 跳过 P/B 帧，省 80% 解码量 |
| 3 | CPU 均匀抽 N 帧（N=5-8） | ~3-5s | 兜底，最慢但最兼容 |

每个片段抽 **5-8 帧**送 YOLO 即可：移动侦测片段通常 30秒-3分钟，5-8 帧足以覆盖"有没有人经过"。

### 3.3 动静检测：背景建模而非帧差

固定机位下用 **MOG2 背景减除**（`cv2.createBackgroundSubtractorMOG2`）：

- 比帧差鲁棒：能吸收"一直在晃的树叶"等持续背景噪声
- 输出前景掩码 → 可算前景面积占比、质心位置、时间持续性
- 速度快，CPU 即可

用途：不是判断"有没有动静"，而是刻画**误触发指纹**（v2 增强项）。

### 3.4 打分制而非布尔阈值

**保留价值分 `retention_score`（0-100）**：

| 信号 | 加分 | 说明 |
|------|------|------|
| 检出 `person` | +50 × 置信度 | 权重最高 |
| 检出 `vehicle` 类 | +40 × 置信度 | |
| 检出 `animal` 类 | +15 × 置信度 | 可配置是否计分 |
| 前景面积占比 > 5% | +10 | 大面积运动更可能是真实事件 |
| 音频能量超阈值（若有音轨） | +10 | |

**分流规则**：
- `score == 0` → **高置信无效**，进"建议清理"队列
- `0 < score < 30` → **可疑**，进人工审核队列，**按分数升序排**（最可疑的先看）
- `score >= 30` → 保留

> 分数只需用于**排序**，不需要绝对精确 —— 因为删除前必然经过人工确认。这让它容错性很高。

### 3.5 VLM 二次复核（8GB GPU）

#### 3.5.1 定位：降误删，而不是提清理率

YOLO 是目标检测器，在**夜视/红外、遮挡、俯视角小目标、低分辨率**下会漏检 —— 漏检就等于把有用录像判成垃圾，也就是误删。

在"宁可多留不可误删"的红线下，二次复核的**首要价值是把 YOLO 漏检的捞回来**，其次才是提高清理决策的置信度（让人批量通过时更放心）。这个定位决定了后面所有设计。

#### 3.5.2 三级漏斗：VLM 只在候选集上跑，绝不全量

```
全量片段      N 万
   │  [L1: YOLO 快速筛]     ~0.3s/个    便宜，可全量
   ▼
候选集        约 10-30%      (score 低 = 疑似无目标)
   │  [L2: VLM 二次复核]    ~1-3s/个    只在候选上跑
   ▼
待人工确认    约 1-5%
   │  [L3: 人工确认 + 撤销]
   ▼
清理
```

VLM 比 YOLO 慢 100-1000 倍，**绝不能全量跑**。因为它只处理候选集（总量的 10-30%），总成本可控 —— 每批 1-3 万片段，候选 2000-6000 个，串行 1-5 小时、开并发后 20-70 分钟，完全可接受。

#### 3.5.3 模型选型（8GB 显存）

| 模型 | 参数 | Q4 体积 | 8GB 适配 | 说明 |
|------|------|---------|---------|------|
| **Qwen3-VL-4B** ⭐ | 4B | ~3.3 GB | **宽裕** | 首选。中文原生、Apache 2.0、权重小，留出 4GB+ 给视觉编码器与 KV cache |
| Qwen3-VL-8B | 8B | ~5-6 GB | 紧张 | 精度更好，但 8GB 卡上必须压上下文 + 降分辨率 |
| InternVL3.5-8B | 8B | ~5 GB | 紧张 | 视觉推理强，中文与部署生态弱于 Qwen |
| Moondream 3.1 | 9B 总参 / 激活 2B | ~5 GB | 宽裕 | 原生 `detect`/`point` 结构化技能，若只需"有没有人"的二值判断，它最快最可控 |
| Gemma 4 12B QAT | 12B | ~7 GB | 极紧 | 不推荐，8GB 卡余量不足 |

**推荐 Qwen3-VL-4B-Instruct（GGUF Q4_K_M）**，理由：8GB 卡上 4B 才有足够余量给视觉 token 展开和 KV cache（视觉模型的显存大头不是权重，是图像 token）；Apache 2.0 许可无商业限制；中文原生，prompt 用中文写判断更准。

> ⚠️ **量化不低于 Q4**。视觉任务压到 IQ4_XS 后，OCR 和小目标识别开始出低级错误 —— 精度敏感的视觉任务，Q4_K_M 是底线。

#### 3.5.4 Windows 部署框架

vLLM 吞吐最高但**不支持原生 Windows**（需 WSL2/Docker），Windows 下二选一：

| 框架 | 适用 | 说明 |
|------|------|------|
| **llama.cpp `llama-server`** | 批量生产 | Windows 有 CUDA 预编译版；用 `-np N` 开多并行 slot 提吞吐；OpenAI 兼容 API |
| **Ollama** | 快速验证 | 零配置（`ollama run qwen3-vl:4b`），自带 API，但并发调度不如 llama.cpp 可控 |

建议：**先用 Ollama 验证效果，确定后换 llama.cpp 跑批**。

#### 3.5.5 输入方式：帧拼网格，不用原生视频输入

Qwen3-VL 虽支持原生视频输入，但瓶颈在**帧数带来的视觉 token 与 KV cache 膨胀**。做法：把抽出的 6 帧拼成 **2×3 网格图**（每格 640×360，总图 1280×1080），**一次推理看完整段**。

- 显存可控（单张图输入）
- 一次推理覆盖整个片段，成本从 6 次降到 1 次
- 若担心小目标分辨率不足，可只对"YOLO 有低置信度检出但分数不够"的片段做单帧高分辨率复问

#### 3.5.6 采样参数（实战验证值）

```
关闭 thinking
temperature 0.1 / top_p 0.1 / top_k 10
max_model_len 压到 8K（默认 262K 纯浪费显存）
输出强制 JSON（固定字段）
```

#### 3.5.7 Prompt 设计（关键：给模型一个保守偏置）

```
你是监控录像审核助手。以下是同一段录像的 6 个关键帧（按时间顺序拼接）。
只输出 JSON，不要任何解释：

{
  "has_person": true/false,
  "has_vehicle": true/false,
  "confidence": 0-100,
  "evidence": "只描述你确实看到的画面内容，不超过 30 字"
}

规则：
1. 任意一帧出现人（含远处、遮挡、模糊人影），has_person 即为 true
2. 不确定时一律返回 true —— 宁可误留，不可误删
3. 不要推测画面之外的事件，不要描述时间戳水印和边框
```

**第 2 条是整个方案里最便宜的一道保险** —— 用一个 prompt 偏置，把模型的判断方向强行扭向"保守保留"，直接对齐"宁可多留不可误删"的红线。第 3 条防的是这类场景最大的坑：**模型把环境推测写成事实**。

#### 3.5.8 已知翻车场景（务必纳入 Phase 3 校准）

| 场景 | 表现 |
|------|------|
| 模糊 / 低照度画面 | 小模型直接"看不到人"，需单独调阈值 |
| 背景小目标 | 画面角落的目标被漏检（主场景描述全对，就是丢了角落的东西） |
| 量化过低 | IQ4_XS 下小目标识别出现低级错误 |
| 幻觉 | 描述出不存在的目标 —— 靠 JSON 格式约束 + 保守偏置压制 |

> 这些场景**必须用你自己的历史画面做误报/漏报统计**，公开榜单分数替代不了这一步。

### 3.6 音频复核层：有声事件捞回（2026-09-05 新增）

**定位 —— 与 VLM 互补的第二个"捞回"维度**

画面判定"无目标对象"只能说明**看不到**人/车，不能说明**听不到**内容。监控误触发里常混着"画面无人但有声"的真实事件：

- 室内固定机位拍不到门口，但有人在画外打电话 / 争吵 / 对讲
- 店门口机位只拍到空景，顾客在画面边缘外说话、询价
- 门铃、广播、警报、车辆鸣笛等声音事件（无人入镜）

这些片段视觉上会被 YOLO 判"无目标"从而进回收档，但声音里记录了事件，**删了就丢**。音频复核的价值 = 在删除前捞回"有声事件"，与 VLM（捞回"画面有人但漏检"）形成两个正交的兜底维度。

**适用范围与漏斗位置**

```
L1 YOLO 画面判定 ── 有目标 ──────────────► 保留
     │
     └─ 无目标（判删候选 A/B 档）
          │  has_audio=0 ───────────────► 直接进回收档（无声音可复核）
          │  has_audio=1 ──► [L2.5 音频复核]：VAD 人声检测 → ASR 转写
                                  │
                    ┌──────────────┴──────────────┐
              无人声 / 无内容                有人声（说话/播报…）
               │  LLM：内容无用                  │
               ▼                                ▼
          确认判删，进回收档               拦下，标记"有声事件"，
                                           审核台展示转写文本供人查看
```

**复核管线（单段）**

1. **抽音轨**：ffmpeg `-vn -ac 1 -ar 16000 pcm_s16le` → `work_dir/audio/{video_id}.wav`（中间产物，复核后可清理）
2. **人声分段**：FSMN-VAD（达摩院）→ 输出"有无人声、语音段起止时间戳、语音占比"。**这一步直接回答用户第一问"声音中是否有说话内容"**
3. **转写**：Paraformer-zh（阿里 ASR，中文监控低质音频鲁棒性优于 whisper-small）逐语音段转写，带时间戳
4. **标点**：ct-punc 加标点（可选，便于人读）
5. **LLM 有用性判断**：把转写文本 + 元数据（时间/时长/频道）送本地 ollama（qwen3:4b），保守偏置 prompt，强制 JSON 输出 `{useful: bool, reason: str, event_type: str}`。**LLM 结论只是参考，最终由人拍板**

**技术选型与理由**

| 项 | 选型 | 理由 |
|---|---|---|
| ASR 引擎 | **FunASR（阿里达摩院）** | 中文专精抗噪、自带 VAD 分段、ModelScope 国内分发免代理 |
| 运行后端 | **GPU torch（CUDA）** | RTX 3070 Ti 8GB 足够；批量转写实时率 10-30x |
| LLM | **ollama + qwen3:4b** | 本地离线免费；与 vlm 段共用 11434 端点 |
| 音频抽轨 | ffmpeg 8.1 | 已在 PATH，`-ss` 采样避免全量解码长片段 |

**引擎可插拔**：`audio.engine = "funasr" | "faster_whisper"`。FunASR 若在 Python 3.13 上装不上，降级 faster-whisper（ctranslate2 自带 CUDA，不需 GPU torch）。

**成本估算**：VAD ~100x 实时、ASR GPU ~10-30x 实时。1 万段 × 平均 3 分钟 ≈ 后台连续 5-10 小时，可中断、断点续跑（只处理 `audio_checked=0`）。

**红线（与全系统一致）**

- 音频复核只**拦下/放行**，不删除、不移动；移动仍走现有 A/B 回收目录 + 人工确认
- VAD 判"无人声" ≠ 立刻删：还要 LLM 对无语音段给结论 + 人可抽查（`B_低置信` 本来就要抽查）
- ASR 文本仅用于查看与 LLM 判断，**不写入任何会被当作"铁证"的判定**；有说话内容一律先给人看

#### 3.6.1 数据模型（videos 表新增列）

| 列 | 含义 |
|---|---|
| `audio_checked` | 0 未复核 / 1 已复核 / -1 无音轨跳过 |
| `speech_present` | VAD 是否检出人声（0/1） |
| `speech_ratio` | 语音时长占比 |
| `speech_segments` | VAD 分段 JSON（起止时间戳） |
| `transcript_text` | 转写全文（给人看） |
| `transcript_segments` | 段级时间戳 JSON |
| `llm_useful` | LLM 判断（1 有用/0 无用/2 不确定） |
| `llm_reason` | LLM 理由（展示给用户） |
| `audio_error` | 复核失败原因（技术失败默认保留，不判删） |
| `audio_checked_at` | 复核时间 |

#### 3.6.2 UI 形态

- 审核工作台对判删候选增加**音频复核状态卡**：语音有无 / 语音占比 / 转写全文（时间戳可展开）/ LLM 结论与理由 / 播放抽出的音频（st.audio）
- 「确认清理」按钮在 `has_audio=1` 且未复核时**提示先复核**；复核为"有人声/LLM 判有用"的片段默认建议保留，文本强制展示给用户看
- 「设置与扫描」页：音频引擎开关、复核范围、LLM 连接自检

#### 3.6.3 指标与验收

- **说话检出抽查**：人工抽查 N 段复核为"无人声"的样本，确认 VAD 未漏（目标漏检 < 1%）
- **有声捞回率** = 复核为"有说话内容"的片段 / 判删候选总数 —— 直接回答"这层值不值得做"
- **LLM 有用性抽查**：对 `llm_useful=0` 的段人工复看文本，统计误判率（LLM 只是建议，红线在人工）

### 3.7 移动安全 —— 程序永不删除

**程序职责边界**

| 阶段 | 谁做 | 性质 |
|------|------|------|
| ① 分析、打分、排序 | **程序** | 只读 |
| ② 移入**分级**回收目录 | **程序** | 一键撤销 |
| ③ 真删释放空间 | **用户手动** | 不可逆 |

**程序永不执行 delete / format 或任何不可逆操作。**

#### 3.7.1 分级回收目录：让手动删除变得简单

既然第 ③ 步由人来做，回收目录的组织方式就**要给人类看**，按 AI 置信度分级：

```
_Trash/
├── A_高置信_可批量删除/       ← L1 score=0 且 L2 VLM 一致确认无目标
│   └── <原相对路径>/
├── B_低置信_建议抽查/         ← 仅 L1 判无目标，或两级存在分歧
│   └── <原相对路径>/
└── _reports/
    ├── 移动清单_<批次>.csv     ← 原路径 / 新路径 / 判定依据 / 分数 / 缩略图位置
    └── 空间统计_<批次>.txt     ← 各年份目录移走的文件数与容量
```

用户手动删除时的操作路径变得极简：

- **A 目录 → 直接全选删除**（两级 AI 一致确认无目标）
- **B 目录 → 抽查后再删**（对照清单里的缩略图）

> 这个设计的价值：把 AI 的**置信度直接映射成文件系统结构**，让人不必回头查数据库，对着文件夹名就能决定删哪个。

**分档规则**

| 档位 | 条件 |
|------|------|
| **A 高置信** | `retention_score == 0` **且**（未启用 VLM，或 `vlm_agree=1 且 vlm_has_person=0 且 vlm_has_vehicle=0`） |
| **B 低置信** | 其余经人工确认移动的（仅 L1 判定、两级有分歧、置信度偏低） |
| **不移动** | 解不开 / 报错的片段 —— **默认保留**，绝不因技术失败而误删 |

**硬约束**

- 回收目录**必须在同一个移动硬盘上**，否则跨盘 move 就是复制 10TB
- 移动时**保留原目录结构**，杜绝重名覆盖
- 全量 `action_log` 记录 原路径 → 新路径，**支持一键撤销**（按批次 / 按文件）
- 单批次移动上限（如 500 个），防止误操作波及全库
- 每批次移动后**自动生成清单 CSV**，供手动删除时对照抽查

### 3.8 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 数据 | **SQLite** | 几十万行无压力，零运维 |
| L1 快筛 | Python + OpenCV + Ultralytics YOLOv8n | 独立 CLI 进程，可脱离 UI 长期后台跑 |
| L2 复核 | **Qwen3-VL-4B** (GGUF Q4_K_M) + llama.cpp server | 8GB GPU，只在候选集上跑 |
| 元数据 | **ffprobe** | 只读 header，不解码，秒级 |
| UI | **Streamlit** | 单用户本地工具足够 |
| ~~FastAPI~~ | **砍掉** | 原方案 Streamlit + FastAPI 双层冗余；"流式展示"本质是前端轮询数据库，与 FastAPI 无关 |

**架构原则**：分析引擎与 UI **完全解耦**。引擎是 CLI（`python analyzer.py --batch 1 --vlm`），写完库就退出；UI 只读数据库。这样引擎可以在服务器/后台跑几天，UI 想开就开。

## 4. 数据库设计

```sql
-- 视频主表
CREATE TABLE videos (
    id               INTEGER PRIMARY KEY,
    path             TEXT    UNIQUE NOT NULL,
    filename         TEXT,
    rel_dir          TEXT,            -- 相对根目录的路径，用于分批 & 回收时保留结构
    size_bytes       INTEGER,
    mtime            REAL,

    -- ffprobe 元数据（Phase 0 填充）
    duration_sec     REAL,
    width            INTEGER,
    height           INTEGER,
    video_codec      TEXT,            -- hevc / h264 / 私有编码标记
    has_audio        INTEGER,         -- 关键：多数摄像头不录音，此维可能全程为 0
    bitrate_kbps     INTEGER,

    -- AI 分析结果（Phase 2 填充）
    has_person       INTEGER,
    person_conf      REAL,
    has_vehicle      INTEGER,
    vehicle_conf     REAL,
    has_animal       INTEGER,
    motion_area_ratio REAL,           -- 前景面积占比
    sampled_frames   INTEGER,
    retention_score  REAL,
    analyzed_at      TEXT,
    analyze_error    TEXT,            -- 解码失败/私有编码不兼容，单独标记不阻塞队列

    -- L2 VLM 二次复核（Phase 2.5 填充，仅候选集有值）
    vlm_has_person   INTEGER,
    vlm_has_vehicle  INTEGER,
    vlm_confidence   REAL,
    vlm_evidence     TEXT,            -- 模型给出的依据，人工审核时直接展示
    vlm_agree        INTEGER,         -- 与 L1 是否一致：1=一致 / 0=分歧
    vlm_model        TEXT,            -- 记录模型版本，便于回溯
    vlm_reviewed_at  TEXT,

    final_score      REAL,            -- L1 与 L2 合成后的最终保留价值分，UI 按此排序

    -- 流程状态
    status           TEXT DEFAULT 'pending',  -- pending/metadata/analyzed/keep/trash
    batch_id         INTEGER,
    reviewed_at      TEXT,
    trash_path       TEXT                     -- 用于撤销
);

CREATE TABLE batches (
    id          INTEGER PRIMARY KEY,
    name        TEXT,
    root_dir    TEXT,
    filter_rule TEXT,        -- 目录/日期/大小筛选条件
    created_at  TEXT,
    status      TEXT,        -- scanning/analyzing/reviewing/done
    total       INTEGER,
    analyzed    INTEGER
);

CREATE TABLE action_log (    -- 撤销能力的基础
    id         INTEGER PRIMARY KEY,
    video_id   INTEGER,
    action     TEXT,         -- move / keep / undo
    from_path  TEXT,
    to_path    TEXT,
    batch_id   INTEGER,
    created_at TEXT
);

CREATE INDEX idx_videos_status ON videos(status);
CREATE INDEX idx_videos_score  ON videos(retention_score);
CREATE INDEX idx_videos_final  ON videos(final_score);   -- UI 审核队列主排序
CREATE INDEX idx_videos_agree  ON videos(vlm_agree);     -- 快速捞出"两级分歧"样本
CREATE INDEX idx_videos_batch  ON videos(batch_id);
```

**关键字段说明**：
- `analyze_error` —— 私有编码（H.265+/Smart H.265）可能解不开，必须单独标记而非让整个队列卡死
- `rel_dir` —— 回收时重建目录结构的依据
- `trash_path` + `action_log` —— 撤销的两道保险

## 5. 开发阶段计划

### Phase -0.5：硬盘健康检查与备份决策 🔴 最高优先级
**工作量**：1 小时 | **阻塞之后所有阶段**

- [ ] 查移动硬盘 **SMART 状态**（CrystalDiskInfo）：重映射扇区计数、待映射扇区、CRC 错误计数、通电时间
  - 若存在坏道 / 重映射持续增长 → **立即停止筛选，优先抢救数据**
- [ ] 决策：是否购入第二块盘做完整备份（强烈建议，见 0.5.2）
- [ ] 规划回收目录：必须与源**同一移动硬盘**，确认剩余空间足以容纳待清理数据
- [ ] 确认本地 SSD 空间：数据库 + 缩略图（估算：每片段 6 帧缩略图约 200KB，1 万片段 ≈ 2GB）

**验收**：硬盘健康报告 + 备份方案拍板 + 目录规划完成。

### Phase -1：NVR 事件数据探测（若设备仍在）

**工作量**：1 小时 | **前置**：Phase -0.5

> 数据既已脱离 NVR，此步价值有所下降。但 **NVR 的事件日志与录像是分开存储的** —— 录像清空不代表日志没了，仍值得花 1 小时确认。

- [ ] 确认 NVR 设备是否还在、能否开机
- [ ] 查事件日志能否导出 / 能否按人形检测筛选
- [ ] 抽查移动硬盘上的文件命名规则，是否含事件类型字段

**出口决策**：能拿到事件数据 → 走轻量路线；否则走完整路线。

### Phase 0：元数据盘点（不写一行 AI 代码）
**工作量**：半天 | **前置**：Phase -1 确认走完整路线

- [ ] `ffprobe` 抽样扫描（先扫 1 个目录，不全量）
- [ ] 输出盘点报告：真实文件数、片段时长分布、码率、分辨率、**有无音轨**、**编码是否为 H.265+ 私有格式**
- [ ] 实测单片段解码耗时，确定走 GPU 硬解 / 关键帧 / 均匀抽帧哪一条

**验收**：得到一张表，回答"到底多少文件、能不能解开、多快能跑完"。

### Phase 1：数据底座
**工作量**：1-2 天

- [ ] SQLite schema + 索引
- [ ] 扫描器：支持按目录/日期分批、断点续跑
- [ ] ffprobe 元数据批量入库（并发读 header，不解码）

**验收**：扫描一个真实目录，库里元数据齐全，重复运行不产生脏数据。

### Phase 2：分析引擎 v1
**工作量**：2-3 天

- [ ] 抽帧模块：GPU 硬解优先，自动降级（3.2 的三级策略）
- [ ] YOLOv8n 目标检出（person / vehicle / animal）
- [ ] MOG2 前景面积统计
- [ ] `retention_score` 计算
- [ ] CLI：`python analyzer.py --batch N --device cuda`，进度落库，可中断续跑

**验收**：CLI 跑通一个目录，速度达标（GPU ≥ 3 片段/秒，CPU ≥ 0.3 片段/秒），断点能续。

### Phase 2.5：VLM 二次复核层
**工作量**：1-2 天 | **前置**：Phase 2 产出候选集 | **可跳过**：见下方捞回率判据

- [ ] 部署 Qwen3-VL-4B（Ollama 验证 → llama.cpp 跑批，`-np` 并发）
- [ ] 帧拼网格（2×3）生成模块
- [ ] VLM 客户端：固定 JSON schema、`temperature 0.1`、保守偏置 prompt（3.5.7）
- [ ] `vlm_agree` 分歧检测：**L1 与 L2 结论不一致的样本强制进人工队列** —— 这类分歧样本正是模型最没把握的，也是最容易误删的
- [ ] `final_score` 合成逻辑
- [ ] 实测吞吐，定并发 slot 数

**核心指标：捞回率** —— 在 L1 判为"无目标"的候选中，VLM 重新检出人/车的比例。

> 这个数字**直接回答"二次复核到底值不值"**：若捞回率 < 1%，说明 L1 阈值已经够准，二次复核应降级为可选项，把时间省下来。

**验收**：单批候选（2000-6000 个）1 小时内跑完；产出《捞回率报告》。

### Phase 2.6：音频复核层（有声事件捞回）
**工作量**：2-3 天 | **前置**：Phase 2 | **设计**：见 3.6

- [ ] 引擎安装链：torch CUDA 版 + FunASR（fsmn-vad / paraformer-zh / ct-punc，ModelScope 国内下载）；失败降级 faster-whisper
- [ ] `src/audioreview.py`：ffmpeg 抽音轨 → VAD 人声分段 → ASR 转写 → LLM（ollama qwen3:4b）有用性判断（保守偏置 + 强制 JSON）
- [ ] videos 表新增 3.6.1 所列复核字段（老库 migrate）
- [ ] 后台任务 `audio` kind：只处理判删候选（A/B 档）且 has_audio=1、未复核的片段；可中断续跑
- [ ] 审核台音频复核卡：语音占比 / 转写全文（时间戳）/ LLM 结论 / 播放抽出的音频
- [ ] 处置关口：判删候选未过音频复核时「确认清理」提示；检出人声的片段强制人看文本后再定
- [ ] 音频中间产物（work_dir/audio/）管理与清理
- [ ] selftest 回归：字段 migrate、judge 决策、无音轨/全静音样本、UI 接线

**核心指标：有声捞回率** —— 复核为"有说话内容/有用"的片段占判删候选的比例。
**验收**：跑通 100 段真实判删候选；抽查 20 段"无人声"结论 VAD 漏检 < 1 段；产出《有声捞回率报告》。

### Phase 3：阈值校准 🔴 决定项目是否可用
**工作量**：1-2 天 | **前置**：Phase 2（+ 2.5 若启用）

- [ ] 抽取 **200-500 个**代表性样本（覆盖白天/夜晚/雨天/逆光等不同光照）
- [ ] 人工标注 ground truth
- [ ] 统计：误删率（把有用的判成垃圾）、漏删率（垃圾没抓到）
- [ ] **重点复检两级分歧样本**（`vlm_agree = 0`）与 VLM 捞回样本
- [ ] 调阈值与权重

**这是必须的一步**。跳过它直接上全量，等于拿 10TB 数据赌一个没验证过的阈值。

**验收**：误删率 < 1%（宁可漏删，不可误删），并产出一份《阈值校准报告》。

### Phase 4：Streamlit 审核台
**工作量**：2 天

- [ ] 队列视图：按 `retention_score` 升序，最可疑的排最前
- [ ] **九宫格缩略图**批量模式（关键帧拼图，不播原片 —— 规避 H.265 浏览器兼容问题）
- [ ] 单条详情：关键帧序列 + 元信息 + AI 判定理由
- [ ] 键盘快捷键（Space=清理，Enter=保留），批量勾选一次提交 50-100 个
- [ ] 侧边栏：批次进度、已回收空间统计

**验收**：审核 100 条的耗时 < 10 分钟。

### Phase 5：移动执行、撤销与清单导出（**不含删除**）

**工作量**：1 天

> **程序不实现删除功能** —— 只做区分和移动，删除由用户手动完成（见 3.6）。

- [ ] 分级回收目录：`A_高置信` / `B_低置信`（分档规则见 3.7.1）
- [ ] 移动时保留原目录结构，同盘 move
- [ ] `action_log` 全量记录 + **一键撤销**（按批次 / 按文件回滚）
- [ ] 单批次移动上限保护
- [ ] 每批次自动生成**移动清单 CSV**：原路径 / 新路径 / 判定依据 / 分数 / 缩略图位置
- [ ] 空间统计报告：各年份目录移走的文件数与容量

**验收**：
1. 刻意撤销一次，文件完整回到原位
2. 导出的清单能对着抽查缩略图
3. **代码审计确认：全库无任何 `os.remove` / `shutil.rmtree` / `unlink` 调用** —— 这是"程序永不删除"的硬保证，建议用 grep 做成 CI 检查

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **移动硬盘掉盘 / 过热** | 长时间连续读写中断，甚至数据损坏 | 按年份分批 + 断点续跑 + 批间停歇；产物写本地 SSD；跑前查 SMART |
| **误删后无法恢复**（数据唯一） | 永久丢失，无任何补救手段 | **程序不做删除**，只移动到 A/B 分级回收目录；移动 100% 可撤销；每批次导出清单供人工核对；代码审计禁止 delete 调用。**最根本的对策仍是 Phase -0.5 的备份** |
| **H.265+ 私有编码解不开** | 分析直接失败 | Phase 0 优先探测；`analyze_error` 单独标记，不阻塞队列；解不开的**默认保留**（绝不因技术失败而误删） |
| **浏览器播不了 H.265** | 人工审核链路断裂 | 审核台**不播原片**，用关键帧缩略图；确需看片时调起本地播放器 |
| **误删关键证据** | 不可逆损失 | 三道保险：move 不 delete + 完整日志 + 一键撤销；单批次上限；Phase 3 校准把关 |
| **跨盘移动极慢** | 回收比分析还慢 | 强制回收目录与源同盘 |
| **文件名重名覆盖** | 静默丢数据 | 保留原目录结构 |
| **模型在夜视/红外下失效** | 夜间片段大量漏检 | Phase 3 样本必须覆盖夜间；红外画面下 person 检测置信度显著降低，需单独设阈值 |
| **VLM 幻觉** | 描述出不存在的目标，结论不可信 | 强制 JSON 输出 + 保守偏置 prompt（不确定即返回 true）+ 人工确认兜底 |
| **VLM 全量跑导致工期失控** | 比 YOLO 慢 100-1000 倍 | 架构限制：只在 L1 候选集上跑；代码层加硬门槛，高分片段绝不进 L2 |
| **量化过低导致精度崩塌** | 小目标识别出现低级错误 | 量化不低于 Q4_K_M，不用 IQ4_XS |

## 7. 验收标准（整体）

1. 分析引擎可脱离 UI 后台运行，支持中断续跑
2. 单个批次从扫描到产出审核队列全自动，无需人工干预
3. **误删率 < 1%**（Phase 3 校准报告佐证）
4. 程序**不含任何删除功能**；移动操作 100% 可撤销；每批次自动导出清单 CSV 与空间统计
5. 审核效率：熟练后单批次（约 1 万片段）人工审核 < 4 小时
6. **VLM 复核可一键开关** —— 它是增强层，不是依赖层，关掉不影响主流程
7. **移动硬盘全程只读**（除执行清理的那一次批量 move），数据库 / 缩略图 / 日志全部落本地 SSD

## 3.9 语音档案 —— 删除前抢救音频资产

> 需求背景：视频（画面）对机主没有保存价值，但里面的人声对话今后可能用于
> ASR 训练或资料检索。在用户手动清空回收目录这一不可逆动作之前，把
> 「有效语音」的音频 + 转写文本持久收藏。访谈定案记录见 CONTEXT.md。

### 3.9.1 设计决策（访谈定案）

| 决策点 | 结论 | 依据 |
|---|---|---|
| 入档线 | `speech_present=1`（有效语音） | LLM 有用性误判不可逆，宁多存；useful 仅作档案标签 |
| 圈定范围 | `human_decision='trash'` 且 `trash_path` 非空（已移入回收目录） | 程序移动时自写该状态，撤销移动自动排除，无需删除对账 |
| 数据源 | 复核缓存 wav（`work_dir/audio/{id}.wav`）+ 数据库转写 | 视频被手动删除后仍可归档，无时间窗压力 |
| 音频形态 | 16kHz 单声道原始 wav，直接复制零转码 | ASR 训练标准格式；真实声学条件；降噪副本可随时再生不归档 |
| 配对文本 | 同名 `.txt`（= `transcript_text`） | ASR 训练标准"音频+文本对"形态，人也易读 |
| 目录组织 | `{archive_dir}/{年份}/{原文件名stem}.wav/.txt` | 原文件名=日期_时间_通道，天然唯一带语义 |
| 总清单 | `manifest.jsonl` 追加式（每行一条 JSON） | 训练元数据 / 检索索引 / 幂等第二依据 |
| 存放位置 | 配置项 `archive.dir`，设置页可改，默认 `E:/audio-archive` | 工作盘与缓存分离防误清；**红线：绝不写 G 盘**（删除发生地） |
| 幂等 | `videos.archived_at` 时间戳标记 + manifest 双保险 | 按钮可反复按，只处理增量 |
| 撤销移动后 | 档案保留不回收 | 档案一旦生成即独立资产，宁存勿删 |
| 缓存缺失 | 跳过该行并计入结果报告，不阻塞批次 | 极端情况：视频已删且缓存被清，无法恢复，如实报告 |

### 3.9.2 manifest.jsonl 行格式

```json
{"id": 1586, "src_path": "G://change//2015//20151213//20151213211936_010.mp4",
 "trash_path": "G://need-del//A_高置信_可批量删除//2015//20151213//20151213211936_010.mp4",
 "year": "2015", "duration_sec": 43.5, "speech_ratio": 0.257,
 "speech_segments": [[0.04,2.76],[6.87,9.03]],
 "transcript": "你是干嘛来啊？", "llm_useful": 1, "llm_reason": "[speech] 有对话内容",
 "archived_at": "2026-09-07T13:00:00"}
```

### 3.9.3 架构落点

- **DB**：`videos` 追加 `archived_at TEXT`（migrate 幂等）；新增 `archive_queue()`（谓词查询）与 `mark_archived(id, ts)`
- **配置**：`archive: {dir: "E://audio-archive"}`，load 自动补齐新键
- **后端**：`src/archiver.py` —— `archive_pending(db, cfg, log)` 纯同步实现（复制+写 txt+追加 manifest+标记），供 jobs 调用
- **任务**：`jobs.py` 注册 `archive` 任务类型，走现有进度面板（每次归档量预计数百条、纯本地复制，分钟级）
- **UI**：设置页音频区新增「语音档案」卡片：路径输入（即记即存）+ 待归档/已归档计数 + 「立即归档」按钮（用户要求的"一个按键"）

### 3.9.4 验收标准

1. 幂等：连续按两次，第二次新增 0 条、manifest 不追加重复行
2. 数量守恒：归档数 = trash ∧ speech_present=1 ∧ 缓存 wav 存在
3. 抽查 wav 为 16000Hz 单声道；txt 内容与 DB `transcript_text` 一致
4. 撤销移动（human_decision → keep）后档案文件保留
5. 全程未在 G 盘创建任何文件
6. 进度面板正常显示条数/剩余，中断续跑不重复
