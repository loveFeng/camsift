## 一、系统定位与红线

**做什么**：把家庭监控（动态侦测录制的 DVR 素材）按"值不值得留"分级，把有价值的画面与声音**先保全下来**，
再把垃圾归堆到回收目录，最后由机主手动删除。

**四条不可交易的红线**（改代码前先读这里）：

| 红线 | 落点 | 怎么保证 |
|---|---|---|
| **永不删除** | 全库 | `scripts/selftest.py` 内置代码审计，扫描 `src/` 下不得出现 `os.remove` / `shutil.rmtree` / `unlink`；清理自创临时目录的行必须带 `# AUDIT-OK` 注释 |
| **源盘只读** | `scanner` / `analyzer` / `highlighter` | 数据库、缩略图、产物全部落在别处；源盘只在 `mover.move_one()` 移动时被写一次 |
| **解不开的片段默认保留** | `analyzer` | 解码/探测失败写 `*_error` 并给 `keep` 倾向，绝不因技术失败判垃圾 |
| **删除的时机由机主决定** | 回收目录 | 程序只回答"这一条现在能不能删"（`mover.recycle_state`），不代替机主按删除键 |

## 二、分层与模块

分成 8 层，依赖方向单向向下（交互层 → 编排层 → 领域层 → 基础设施层）：

```
┌─ 交互层 ────────────────────────────────────────────────────────┐
│  src/ui.py        Streamlit 工作台（审核/九宫格/精华复核/进度/误判/设置）│
│  src/cli.py       命令行入口（想脱离 UI 长期跑分析时用）                  │
│  src/hotkeys.py   注入 JS 的键盘快捷键（按按钮文案定位）                   │
├─ 编排层 ────────────────────────────────────────────────────────┤
│  src/jobs.py      后台任务：独立线程 + 进度 + 停止 + 防休眠；一键执行串七阶段 │
├─ 领域层 ────────────────────────────────────────────────────────┤
│  src/scanner.py     L1  元数据：ffprobe 扫描 + 音轨能量              │
│  src/analyzer.py    L1  判定：抽帧 → 动静 → YOLO → 打分 → verdict     │
│  src/audioreview.py L2.5 复核：抽音轨 → VAD → ASR → LLM 有用性        │
│  src/archiver.py    L2.7 保全：有效语音 + 转写 → 语音档案             │
│  src/highlighter.py L2.8 保全：两级检测 → A/B/C 三级画面精华          │
│  src/mover.py       处置：分级移动 + 撤销 + 清单 + 回收目录三态子档     │
│  src/feedback.py    归因：误判回看原始检出 → 归类原因 → 调参建议        │
├─ 基础设施层 ────────────────────────────────────────────────────┤
│  src/config.py     配置加载/原子保存/损坏恢复；COCO 类别；ffmpeg 定位   │
│  src/db.py         SQLite：schema + 迁移 + 队列谓词 + 统计（无删除接口）│
└────────────────────────────────────────────────────────────────┘
```

**为什么按这个切**：每一层回答一个独立问题 —— "是什么文件"（scanner）、"里面有人吗"（analyzer）、
"画外有声吗"（audioreview）、"怎么把要丢的东西留住"（archiver/highlighter）、"该放哪"（mover）、
"机器为什么错了"（feedback）。**判定与保全严格分离**：`analyzer` 只给结论、不碰文件，
`highlighter` 只按结论去剪、不改判定 —— 所以"改检测阈值"不会动到产物，"改产物口径"也不会动到分数。

## 三、一键执行：七阶段数据流

`jobs.PIPELINE_STAGES` 定义链路，**顺序由依赖决定，不可调换**（ADR 0004）：

```
 ① 扫描元数据      source_root ──ffprobe──▶ videos(status=pending→metadata)
        │                                      唯一按「本次上限」分批的阶段
        ▼
 ② AI 分析         metadata ──抽帧/YOLO/打分──▶ verdict(keep|trash|review) + decision_trace
        │
        ▼
 ③ 音频复核        处置候选 ──VAD/ASR/LLM──▶ speech_present / transcript_text
        │
        ▼
 ④ 语音档案归档    有效语音 ──复制 wav+txt──▶ 归档目录 + manifest.jsonl + archived_at
        │
        ▼
 ⑤ 批量放行        「无人物信号」候选 ──move──▶ 回收目录
        │
        ▼
 ⑥ 画面精华剪辑    处置候选 ──两级检测──▶ 精华 mp4 + 自动处置(保留/移入回收)
        │
        ▼
 ⑦ 三堆对齐        回收目录存量 ──align_subdirs──▶ 已剪辑/待保全/无精华 子档归位
```

**顺序为什么不能换**：

| 约束 | 后果 |
|---|---|
| 分析 → 音频复核 / 剪辑 | 后两者的队列都只认已判定的 `trash`/`review`，顺序反了就是空跑 |
| 音频复核 → 语音归档 | 归档的数据源是复核产出的转写与缓存 wav |
| **放行 → 剪辑** | 剪辑的自动处置会搬走**未处置**候选，而放行队列只认未处置 ⇒ 反序 = 放行空操作 |
| **剪辑 → 三堆对齐** | 对齐按保全状态归档，早于剪辑跑会把刚剪出 A/B 的行留在「待保全」里白搬一次 |
| 剪辑 / 重剪 / 对齐 → 手动清空回收目录 | 原片被手动删除即不可逆（ADR 0006） |

**失败语义**（`jobs._run_pipeline`）：单条失败由各阶段自己记录后继续；**阶段级失败立即停整条链**，
因为上游失败会让下游空跑或产出半成品，而面板却显示"做完了" —— 比停下来更危险。
停止 = 当前文件处理完收尾、不进下一阶段；再点一次从断点续跑（各阶段都有幂等标记）。

## 四、一条视频的完整生命周期

```
                     扫描            analyze_one()         音频复核
  (源盘文件) ─────────────▶ pending ────────────▶ analyzed ─────────▶ audio_checked / speech_present
                              │ metadata            │ verdict         │
                              │ (meta_ok=1)         │ keep/trash/review
                              └─ meta_error ⇒ error │
                                                    ▼
                        ┌──────────── 处置分岔 ────────────┐
                        │                                  │
             人类审核（ui）/ 批量放行              剪辑自动处置
                        │                                  │
                        ▼                                  ▼
              human_decision='keep'              keep_full_ratio 超限 ⇒ keep
              human_decision='trash'             auto_dispose ⇒ trash
              + trash_path（文件已移动）              │
                        │                            │
                        └──────────┬─────────────────┘
                                   ▼
                        回收目录内判定「保全状态」
                        clipped 已剪辑 / pending 待保全 / plain 无精华产物
                                   ▼
                        机主手动删除（唯一不可逆的一步）
```

**两个正交的处置维度**（别混）：

- `verdict`（AI 的自动判定：keep / trash / review）—— 机器说的
- `human_decision`（人工或批量放行的处置：NULL / `trash` / `keep`）—— 人（或代表人的自动化）说的

`set_human_decision` 维护一条硬不变量：`human_decision='keep'` ⇒ `trash_path`/`trash_tier` 恒为 NULL
（直写不继承，否则撤销移动后残留的路径会让清单和空间统计错报）。

## 五、保全状态三态（回收目录的组织方式）

机主打开回收目录时**只回答一个问题：「这一条我现在能删吗」**，所以按保全状态分堆：

| 状态 | 常量（`mover`） | 落点 | 处置 |
|---|---|---|---|
| 已剪辑 | `STATE_CLIPPED` | `回收目录\已剪辑\<档位>\<年>\<原目录>\<文件>` | 验完产物即可删 |
| 待保全 | `STATE_PENDING` | `回收目录\待保全\<档位>\<年>\<原目录>\<文件>` | ★ **一个都别删** |
| 无精华产物 | `STATE_PLAIN` | `回收目录\<档位>\<年>\<原目录>\<文件>`（不进子档） | 可直接删 |

- **判据只有一处**：`mover.recycle_state()`。`待保全` 的谓词**就是**两条剪辑队列
  （`highlight_queue` ∪ `rehighlight_queue` ∪ 硬失败行）；`db.pending_highlight_ids()` 只用于交叉核对。
- **`已剪辑` 的判据是 `mover.has_ab_clip()`**：现算 `highlight_clips` JSON 且要求产物 mp4 **此刻仍在**；
  C 级不算（档案不是待办）。UI 现状统计走 `verify=False`（不碰 `G:` 上的文件系统），
  真做决定处（`move_one` / `align_subdirs`）才 `verify=True`。
- **`待保全` 归零 ⇔ 可以放心清空回收目录**。归零的路径：跑完剪辑 + 重剪 → `align_subdirs`。
- 子档名**刻意不带字母**：`A/B` 在项目里同时指回收档位（`A_高置信_可批量删除`）与精华级别（`A_确认`），
  两套无关的东西套在一起就再也读不出哪个是哪个。

> 为什么不用「已剪辑 / 未剪辑」两分：**"没剪出 A/B"的那一大堆里绝大多数其实可以闭眼删**
> （机器跑完确认无命中），把真正危险的那一批淹在里面，等于没有保护。详见 ADR 0006 与 `CONTEXT.md`。

## 六、关键设计取舍（每条都有来历）

| 取舍 | 做法 | 为什么 |
|---|---|---|
| **保存原始检出** | `videos.raw_detections` 存未达阈值的检测 | 只存 `has_person=0` 就永远回答不了"模型其实看到了、只是 conf 0.38 没过线" |
| **判定可解释** | `videos.decision_trace` 逐项记分 | UI 要能回答"为什么判它删"，「误判归因」也全靠它 |
| **重编码而非 `-c copy`** | 剪辑一律重编码（`crf` / `preset` / `gop_seconds`） | 监控 GOP 长，`copy` 会把切点吸附到关键帧，切出来的片段跟要留的时间段对不上 |
| **两级检测** | 粗扫低阈值高密度（不漏）→ 精扫高分辨率（看清） | L1 每段只抽十几帧；全片拉到 1280 精扫不现实，所以分级花算力 |
| **产物分级（A/B/C）** | 用目录表达确定性，而不是让人来筛 | 全自动必然有垃圾；C 级是**档案**不进人工队列，"多留"不等于"多看" |
| **版本号纠偏** | `highlight.version` 是唯一纠偏入口 | 产物口径一变就 bump，已剪行自动回落重剪队列且幂等；**不要**给队列加症状分支 |
| **队列幂等标记** | `status` / `audio_checked` / `archived_at` / `highlight_at` | 中断后重跑不重复劳动，停止点即断点 |
| **每个操作独立开连接** | `db.conn()` 上下文管理器 | Streamlit 多线程下复用连接会出问题 |
| **配置原子写入 + 损坏恢复** | `save_config` 先写临时文件再 `os.replace` | 直接 `open("w")` 会先截断，崩一次就留下 0 字节 `config.json`，下次启动直接崩 |
| **权限只提示不阻止** | `check_ready()`（硬错误，拦截）vs `check_warnings()`（风险，`st.warning` 不禁用） | 删除是机主手动操作，程序不替他做决定（`archiver.is_drive_root()` 判盘根） |

## 七、需求 ↔ 实现 追溯

| 诉求 | 实现落点 | 状态 |
|---|---|---|
| ① 剔除没有人的画面 | `analyzer.build_decision()`（人物权重最高）+ `verdict.release_require_no_person` 硬门（ADR 0003） | ✅ 落地 |
| ② 剔除明显不好的视频 | `analyzer.frame_stats()` 算出模糊/偏暗并落库，**不参与打分**，只在 trash 文案里解释 | ✅ 按现口径已满足：画质差的行绝大多数本来就因"无人"被判删；剩下的「糊但有人」恰恰**不该**删 |
| ③ 保留精彩画面 | `highlighter` 两级检测 + A/B/C 三级产物 + 自动处置（ADR 0001/0006） | ⏳ 机制已落地，新口径批次尚待跑完（见 `待办与风险.md`） |
| ④ 保留所有可用音频 | `audioreview`（有效语音判定）+ `archiver`（语音档案，门 = `speech_present=1`） | ✅ 落地（"可用"= 有效语音，队列无欠账） |
| ⑤ 减少存储空间 | `mover` 分级移动 + 清单 + 空间统计；程序不删除 | ✅ 机制成立，腾空间靠机主手动清空回收目录 |

① 的反向口子（有人的画面被处置）与 ③ 的未兑现部分，都在 [`待办与风险.md`](待办与风险.md) 登记。

## 八、磁盘落点

| 用途 | 由谁决定 | 说明 |
|---|---|---|
| 视频源 | `source_root` | 移动硬盘，**只读** |
| 回收目录 | `trash_root` | **必须与源同盘**，否则 move 退化成复制 |
| 数据库 / 缩略图 / 模型 | `runtime.sqlite_path` + `config.py` 的 `ROOT/data` | 本地 SSD |
| 工作目录（音频缓存等） | `work_dir` | 本地 SSD |
| 语音档案 | `archive.dir` | **红线：绝不能设在源盘/回收盘**（那里会被清空） |
| 画面精华 | `highlight.dir` | 同上 |

> ⚠️ **已知的路径分裂**（在办，见 `待办与风险.md`）：`work_dir` / `yolo_model_path` /
> `audio.model_dir` 曾指向另一棵旧树，而 `yolo_model_path` **只**指向它 —— 删掉那棵"看起来像残留"的树，
> `check_ready` 会报"未找到 YOLO 模型"，L1 与 L2.8 全线停摆。**先把路径统一，再清旧树。**

## 九、扩展点

- **换检测模型**：改 `analysis.yolo_model_path`。新增规格必须先过两道门（装载门 / 尺寸门），
  工具 `scripts/download_model.py --spec <规格>` 会自动逐尺寸 forward 校验。
- **换 ASR 引擎**：`audio.engine` 支持 `funasr`（默认）/ `faster_whisper`（降级兜底）。
- **接下游消费者**：语音档案的 `manifest.jsonl` 是标准元数据出口；画面精华的产物按 `shot_at` 分年。
- **周期合辑**：`scripts/compile_period.py` 是独立下游模块（编排 + 拼接），与 `highlighter`（检索 + 切割）
  职责不重叠，见 [`周期合辑方案.md`](周期合辑方案.md)。
